## 1. Задача и стратегия

Сохранить существующий стек, полезные экраны и бизнес-логику. Укрепить общие правила: кому принадлежат данные, кто вправе их менять, что составляет одну операцию, когда результат считается сохранённым и как система восстанавливается после сбоя. Переписывание приложения, новый state framework, микросервисы или новая очередь сообщений не являются целью.

Работать пакетами причин, а не выполнять 102 независимые локальные правки. Например, ES01, AC03, BC01 и HN03 требуют общей границы сессии; одного дополнительного `setUser(null)` недостаточно. B01/B02/D03 требуют общих транзакционных операций, а не последовательности новых cleanup-запросов. Несколько небольших PR допустимы, если каждый реализует часть согласованного конечного решения и не объявляет всю проблему закрытой преждевременно.

**Первый результат агента — воспроизводимая проверка и краткая спецификация исправляемого правила. Последний — доказательство, что правило соблюдается при успехе, отказе, повторе и конкуренции.**

Не откладывать H01/A01/D01/D02/G01 ради общего косметического рефакторинга. Фундамент из этапа R2 строить в объёме, необходимом для ближайшей операции. Не публиковать исправления как безопасный релиз, пока соответствующие проверки границ доступа и изоляции не пройдены.

## 2. С чего начать: первый рабочий пакет R0

1. Прочитать резюме, подробные карточки ближайшего пакета и ограничения аудита. Сверить текущий commit/diff: изменившиеся пути перепроверить; старые номера строк не считать доказательством текущего состояния.
2. Подготовить карту окружений: локальная разработка, одноразовая тестовая БД, staging API, установленная тестовая сборка, production. Записать только безопасные идентификаторы, не секреты. **Локальный `.env` нельзя считать тестовым:** в документации проекта описано использование production БД при локальной разработке.
3. Зафиксировать сборку/commit, версии БД и применённую схему, seed тестовых данных, server URL тестового клиента. Проверки с мутациями выполнять только в явно определённом тестовом окружении.
4. После поручения реализации запустить разрешённые существующие проверки и записать фактический baseline. Сам исходный аудит ничего не запускал; текущий baseline записан в [журнале R0](notes-r0-test-safety.md). Отделить прежние failures от внесённых. Не менять assertions только ради зелёного baseline.
5. Сделать минимальный harness настоящего PostgreSQL и настоящих HTTP handlers/services. Создание тестового приложения отделить от запуска сервера/фоновых задач; отсутствие сетевых побочных эффектов при импорте должно быть проверяемым.
6. На трёх коротких примерах подтвердить полезность harness: отказ БД в auth middleware (A02), rollback создания проекта при отказе второго write (B02), запрет чужого participant ID (D01). Исходный дефект должен воспроизводиться проверкой до исправления; допустим отдельный reproducer на исходной ветке без коммита падающих тестов в основную ветку.
7. Подготовить пакет R1 и схему транзакционного API R2. Не начинать одновременно переписывать AuthContext, sync и все экраны.
8. Провести первичную инвентаризацию кандидатов на мёртвый код, неиспользуемые зависимости/экспорты и дубли. Сопоставить их с реальными entry points, routes, scripts, конфигурацией и native integration. Пока фиксировать доказательства и назначать пакет, без массового удаления. Результат анализатора — список кандидатов, а не разрешение удалить всё найденное. Не откладывать устранение High ради полного каталога косметических дублей.

**Выход R0:** журнал baseline, изолированная БД, воспроизводимый seed, хотя бы один тест реального обработчика с отказом и один с проверкой прав, согласованные ниже решения и первичный список кандидатов на очистку с границами охвата. Это небольшой рабочий фундамент, не отдельная многонедельная разработка платформы тестирования.

## 3. Решения, которые надо зафиксировать до зависимых изменений

| Вопрос | Рекомендуемый исходный контракт | Что требует решения владельца продукта |
|---|---|---|
| Основная БД | PostgreSQL — основная цель runtime и интеграционных проверок; при настроенном, но недоступном PostgreSQL — явная ошибка, без тихого перехода на другую БД | Если SQLite действительно обещан пользователям/разработчикам как поддерживаемый runtime, либо обеспечить отдельные SQL/schema/adapter проверки, либо явно согласовать прекращение поддержки. SQLite-моки не доказывают PostgreSQL |
| Email/OAuth | Неподтверждённый адрес не даёт доверия и права автоматически объединять аккаунты; связь credentials подтверждается явно | Правила восстановления старых конфликтных аккаунтов, подтверждения смены email и сообщения пользователю |
| Видимость репетиции | Admin управляет репетициями своего проекта; обычный member видит/отмечает только существующее приглашение; право не создаётся самим RSVP | Если нужна открытая самозапись, это отдельная разрешённая функция с отдельной политикой, не случайный побочный эффект respond |
| Значение RSVP | Сохранить фактическую нынешнюю семантику «просмотрено/не просмотрено» и независимый roster | Не превращать yes/no в «принял/отклонил» только из-за устаревшего имени типа |
| Timezone | Один явный режим automatic/manual; date-only отдельно от instant; timezone операции известен обеим сторонам | Политика неоднозначных/несуществующих часов DST и поддержка overnight ввода |
| Импорт/экспорт | Замена/удаление ограничены подтверждённым владельцем и connection; legacy записи неизвестного происхождения не удаляются автоматически | Пользовательский сценарий переноса/повторного подключения старых календарей |
| Offline | Показать draft/ошибку/последнее подтверждённое состояние; не обещать серверное сохранение без подтверждения | Полноценная offline-очередь не обязательна для исправления аудита; вводить только при согласованном продуктовом требовании |
| Android | Проверять readiness в реально поддерживаемом канале распространения | Если Android пока не распространяется, IC01 остаётся явно отложенным до Android gate, а не «исправленным на iOS» |

Агент предлагает конкретный вариант и продолжает независимую работу. Человека привлекать для продуктового выбора, доступа к внешнему сервису или физического действия, а не для разрешения каждой обычной правки. Поручение реализации даёт основание выполнять обычные локальные исправления и проверки в согласованном окружении; оно не равно разрешению менять production данные, отправлять реальные уведомления или выпускать приложение.

## 4. Последовательность пакетов и условия перехода

Порядок отражает зависимости, а не только номер finding. R3/R4 можно вести независимо после R2; R5 можно проектировать параллельно серверным операциям, если API-контракты согласованы. R7 зависит от границ сессии R5 и модели данных R2/R6. В общий модуль одновременно не вносят несогласованные изменения несколько агентов.

### R1. Закрыть опасные границы ввода и исполнения

**Область:** H01/H02/H04, A02, B03/B04, IA01, ID01, IS01/IS02; общая форма ошибок и входных схем для следующих пакетов.

- Admin строит DOM безопасными текстовыми операциями; динамическое значение не становится исполняемым HTML/handler. Убрать зависимость от inline event handlers, согласовать CSP для admin и invite. Исправить все соответствующие sinks, а не один пример bug-report.
- Все async middleware/routes имеют единый путь передачи ошибки в error handler. Валидация типов/размеров/дат предшествует вычислениям и write; ошибки возвращают согласованный 4xx/5xx без секретов.
- Проверки membership и budget диапазона выполняются до разворачивания дат. Лимит привязан к операции/роутеру и действует на все aliases.
- Apple provider при отсутствии ожидаемого audience не принимает вход. TTL действительно читается из проверенной конфигурации. Для нескольких процессов limiter использует общее ограничение, а не независимые memory counters.
- Scanner проверяется безопасными fake-secret fixtures и ошибкой чтения; он не подменяет проверку секретов в логах/коде.

**Переход:** HTML остаётся текстом при показе имени и обращения; рабочие admin actions и invite fallback сохраняются; неверный JSON и DB rejection завершают HTTP запрос; большой диапазон отклоняется до тяжёлого цикла; alias не обходит лимит; чужой Apple audience и пустая настройка отклоняются. Проверить обычный корректный запрос для каждой защиты.

### R2. Сделать БД надёжной основой операций

**Область:** F01/F02/F03/F05, FT01/FT02, FM01/FM02.

- Выбрать canonical путь получения схемы; fresh install и upgrade старой версии дают одинаковые обязательные constraints/indexes. Baseline имеет проверяемые postconditions, а не просто отмечает все SQL-файлы исполненными.
- Исправить engine-specific adapter: явный affected row count; transaction передаёт отдельный `tx`, каждый helper внутри операции использует его; rollback и освобождение connection проверяются настоящим adapter.
- DDL миграции и запись ledger выполняются атомарно там, где движок это допускает; отдельные нетранзакционные шаги явно описаны. У мигратора один исполнитель, проверяемая история и безопасное возобновление.
- Dry mode не создаёт таблицы/файлы и не меняет ledger. Неприменимые комбинации флагов отклоняются.
- Исторические преобразования дат задают исходную timezone явно. Не переписывать бесконтрольно уже применённую миграцию: исправлять существующие данные отдельным проверяемым upgrade шагом.

**Переход:** fresh и upgrade БД проходят одни adapter/HTTP contract tests; отказ между SQL и ledger не оставляет непонятное состояние; dry действительно не пишет; PostgreSQL failure не отправляет запросы в скрытый SQLite fallback. Состояние production после аудита не выводить из test fixture.

### R3. Установить доверие к аккаунту и credentials

**Область:** A01/A03/A04, AC05, HP01/HP02; согласование ID01 с политикой сессий.

- Спроектировать полный путь password registration → доказательство владения адресом → рабочая сессия. Pending account не получает возможности обычного аккаунта. Доставка письма, повтор, срок действия и ошибка доставки входят в сценарий.
- OAuth identity не привязывается автоматически к чужому неподтверждённому password account. Разрешение коллизии включает credentials и старые access/refresh сессии; простое удаление password_hash недостаточно.
- Email/provider registry отражает реальные credentials; unlink проверяет последний пригодный способ входа и сохраняет инвариант при конкуренции. Не считать две строки дублирующего provider двумя независимыми способами входа.
- Общая схема register/update/profile: типы, длины и password policy, locale, timezone, nullable/clear semantics. Email change требует подтверждённого отдельного flow; UI не сообщает об изменении, которое сервер игнорирует.
- Хранение bearer credentials через поддерживаемую защищённую платформенную абстракцию; одноразовая миграция старых значений, очистка, восстановление после отказа. UI caches и профили не считаются доказательством авторизации.

**Переход:** сценарий предварительной регистрации чужого email не сохраняет атакующему доступ после входа владельца; оба конкурентных unlink не удаляют все способы входа; смена пароля и конфликт аккаунта отзывают нужные старые сессии; новая регистрация и вход старого законного пользователя не ломаются. Не помечать все старые email verified массовым backfill без доказательства.

### R4. Объединить права и транзакционные бизнес-операции

**Область:** B01/B02, D01–D04, DF02, G01.

- Единые политики canView/canEdit/canRespond и active roster используются routes, services, batch и recipient selection. Каждый переданный ID проверяется до write; неподходящий список отклоняется целиком, а не молча обрезается.
- Create/update/delete проекта и репетиции, удаление member и изменение roster выполняются как domain operations в одной transaction. Изменение membership не может вклиниться между проверкой и записью и нарушить правило.
- Отсутствующее поле roster означает «не менять», `[]` — «очистить». Инвариант roster не зависит от seen state. Edit draft администратора получает объект через подходящий контракт доступа.
- Повтор после потери ответа не создаёт вторую операцию: ключ идемпотентности привязан к actor/operation/body, сохраняется атомарно с результатом; повтор ключа с другим содержимым отклоняется. Для конкурентного edit — revision и явный conflict.
- Внешние уведомления планируются после commit; durable outbox можно хранить в той же БД. Сеть не удерживает DB transaction. Отказ delivery не откатывает уже подтверждённый доменный факт и не маскируется под успешную доставку.
- Push-token имеет единственного владельца. Передача ownership атомарна, stale registration прошлой сессии не возвращает token прежнему владельцу. Один UNIQUE(token) без проверки актуальности операции этого второго свойства не доказывает.

**Переход:** SQL failure в каждой промежуточной точке даёт полный rollback; повтор и конфликт не создают дубль; неприглашённый member не выдаёт себе доступ; чужой ID не получает busy slot; бывший member не получает новые уведомления; конкурентные регистрации оставляют один актуальный owner.

### R5. Сделать клиентское состояние принадлежащим сессии

**Область:** AC01–AC04, BC01/BC02, DF05/DF06, DP01, ES01, NI03, HN02/HN03, HC01, HP04.

- Один owner/session epoch охватывает user, tokens, API, providers, caches и async jobs. Инвалидировать старое поколение до смены credentials. Результат применяется только в своём поколении; запрос A не подставляет свежий token B из глобального storage.
- Разделить временную недоступность refresh и окончательно недействительные credentials. Не оставлять authenticated UI после окончательной потери сессии.
- Очереди storage и очистка работают в одном owner scope. Query key включает нужные user/project/date/member IDs; отмена запроса дополняется проверкой актуальности результата.
- Контексты проектов/seen/unread/preferences имеют явные reset/hydrate/replace правила. Успешный snapshot может снять ранее выставленный seen, а не только добавить yes.
- Для native операций, которые нельзя отменить физически, сохранить исходного owner и безопасно согласовать поздний результат. Он не становится mapping или записью другого аккаунта. Logout не ждёт бесконечно зависший provider; уже начатые внешние эффекты учитываются явно.
- Типизированные безопасные ошибки/логи; не сериализовать целиком Axios request/config, bearer tokens и calendar payloads.

**Переход:** искусственно задержанные ответы A после logout/login B не меняют B state/storage/server/native mappings; повторное монтирование не создаёт двойной sync/registration; поздний response старого фильтра не заменяет новый; настройки имеют один источник истины и явный manual timezone режим.

### R6. Определить контракт доступности и времени

**Область:** C01–C04, CC01–CC06, DF01/DF04, DD02, DP04.

- Развести civil date, local wall time + IANA timezone и UTC instant. All-day хранит календарный день/диапазон дней; его смысл не меняется через device offset. Общие функции чтения/записи используют один контракт.
- На границе API полностью валидировать весь bulk до первого DELETE. Клиент отправляет только изменённые дни. Для replace нужен server revision дня и конфликтный ответ; отсутствие локальной записи не означает разрешение удалить глобальные данные.
- Сервер сериализует конкурентный replace, включая ещё пустой день. Client draft отделён от baseline; focus/refresh и подтверждение предыдущего save не стирают новые edits.
- Не уничтожать source/type/id записи при визуальной дедупликации. Ручное состояние и внешние ограничения независимы.
- Явно определить half-open границы интервалов, midnight/overnight, multiday, DST gap/fold. Сохранение формы без изменения времени сохраняет исходные instants при поддерживаемых profile/device zones. Clock обновляется при смене дня/возврате приложения.

**Переход:** round trip all-day не удаляет соседний день в UTC−; stale snapshot не перезаписывает нетронутый день; два редактора получают согласованный результат/конфликт; новые edits остаются dirty; «удалить прошлое» не затрагивает будущее; overnight и оба края DST имеют явный ожидаемый результат.

### R7. Сделать синхронизацию восстановимой

**Область:** EI01–EI04, EX01–EX04, ES02, EO01–EO06, HP05; обязательная зависимость ES01/R5.

- У каждого импортированного события/маппинга полная идентичность: account, connection/installation, calendar, internal/external event и occurrence там, где требуется. Device-local event ID нельзя считать глобальным между телефонами.
- Diff и удаление ограничены именованным scope. Серверный reconcile атомарно применяет допустимое изменение; failed read не становится пустым authoritative snapshot. Legacy без надёжного owner/provenance сохраняется для сверки, не удаляется «потому что не найден».
- Единственный sync coordinator владеет очередью и session epoch; все settings writers используют согласованный revision. Повторные запуски не обходят lock после await.
- Экспорт изменяет/удаляет только доказанно принадлежащие приложению события. Совпадение title/time/place не даёт ownership. Mapping не теряется до успешного удаления; перенос хранит pending cleanup старой копии.
- Read имеет отличимые found/absent/unknown результаты; failure update не превращается в успешное adoption старого event. Для импорта/экспорта отдельные результаты и retries; failure одного направления не скрывает результат другого.
- Хранить минимум needed operation state: started/committed/partial/failed и owner/revision. Внешняя native операция не атомарна с сервером: возобновление должно сверять фактический результат и исключать повторное создание после потери ответа.
- `lastAttemptAt` и `lastSuccessfulAt` различаются; success определяется подтверждённым scope. Не вводить полноценный offline engine ради одной надписи.

**Переход:** два устройства не удаляют импорт друг друга; личное похожее событие не изменяется; перенос/recurrence/отказ native provider сохраняют данные и путь retry; выключенный sync не включается старым snapshot; после ухода из последнего проекта свои старые exports очищаются по согласованной политике.

### R8. Сделать доставку уведомлений и её статус честными

**Область:** G02, GC01–GC03, NI01/NI02/NI04/NI05/NI06, GR01–GR05; G01/R4 и session scope/R5 — предпосылки.

- Сервисы возвращают явный delivery result; scheduler не теряет failed return. Разделять inbox commit, provider acceptance, receipt и показ устройством — это разные факты.
- Claim имеет lease/status/revision расписания и восстановление после остановки процесса. Перенос rehearsal делает прежний snapshot непригодным; claim не блокирует новую due date. Параллельные workers не выполняют одну допустимую попытку одновременно.
- Не обещать exactly-once внешнюю доставку без поддержки внешнего сервиса: crash после отправки до записи ack допускает неоднозначность. Задать стабильный delivery ID, bounded retries и проверку результата; документировать остаточный риск дубля и его обработку.
- «Позже», denied permission и failed registration отражаются в UI; повтор регистрации ограничен и привязан к сессии. Inbox имеет доступ к старым unread, явные errors и защиту от поздних responses.
- Cron route и job проверяют смысл результата, а не только HTTP200. GitHub schedule сейчас отключён: его включение — отдельное эксплуатационное решение после проверки этого пакета.

**Переход:** fault injection до/после claim и до/после send не теряет пользователя навсегда; failed delivery не считается sent; перенос не подавляет новое напоминание; receipt ошибки обработаны; «Позже» не вызывает повторный prompt; offline read/delete не выдаёт ложного подтверждения.

- Edit draft не доступен для destructive submit до полной корректной загрузки; одна модель RSVP на list/details; выбор planner действительно передаётся в форму.

Для каждого кандидата записать решение «удалён / сохранён с причиной / требует проверки» и подтверждения. **Переход:** выполнены device cards применимых платформ и совместимость старого установленного клиента с новым backend; весь реестр имеет честные статусы и подтверждения. Оставшиеся DEFERRED/BLOCKED перечислены с влиянием на выпуск.

## 5. Алгоритм одного пакета: повторять для каждого R

1. **Сформулировать правило.** Пример: «у каждого push-token один актуальный owner, поздняя регистрация прежней сессии не может его изменить». Перечислить readers/writers/schema/UI и все finding IDs, которые пакет закрывает.
2. **Спроектировать конечный контракт.** Короткая записка: вход/выход, nullable/empty semantics, авторизация, owner/revision, граница transaction, ошибки, повтор, параллельность, миграция старых данных, совместимость старых клиентов. Новый механизм вводится только с объяснением, почему существующего недостаточно.
3. **Показать исходный сбой.** Детерминированный regression test/reproducer против production implementation; зафиксировать результат до изменения. Race-тесты используют barriers/deferred promises/две DB connections, а не случайный sleep.
4. **Реализовать вертикальный сценарий.** Schema → service → route → client → документация там, где нужны изменения. После перевода всех потребителей на согласованную реализацию удалить заменённый путь в этом же пакете и проверить отсутствие обходных callers. Дубли с расходящимися правами/сессией/синхронизацией устранять в соответствующем архитектурном пакете; обычное внешнее сходство кода не требует общего abstraction. Не оставлять временно несовместимый server/client между отдельными deploys; совместимость старого клиента не считать мёртвым кодом до завершения её срока поддержки.
5. **Проверить пять классов исходов:** обычный успех; invalid/unauthorized; отказ в промежуточной точке; повтор после потерянного ответа; две операции в разном порядке. Для destructive scope дополнительно доказать, какие чужие/соседние данные сохранились.
6. **Проверить реальное состояние.** Не только HTTP status/Alert: таблицы и relations после операции, owner/revision/mappings, client cache, native calendar и delivery result в зависимости от сценария.
7. **Выполнить адресные проверки и необходимые общие gates.** Проверки типов/lint без auto-fix, relevant tests, настоящий DB integration, затем необходимые builds/device cards. Полную батарею повторять при изменении общих модулей/границ, а не после каждого изменения текста.
8. **Независимо проверить diff.** Ищем новый обход правила, ошибки rollback и миграции, последствия для старого клиента, утечку данных в тестовые логи. Обновить реестр только с ссылками на evidence.
9. **Передать человеку конкретную карточку**, если остаётся физическое/продуктовое действие. Пока ждём — продолжать независимые задачи; отсутствие ответа не считать успешной проверкой или согласием на deployment.
10. **Завершить пакет.** Указать что изменилось, какие ID закрыты, что действительно запускалось, что осталось NOT_RUN/BLOCKED и какой следующий пакет разблокирован.

## 6. Непереговорные технические правила

- Не отключать падающие проверки, не ослаблять права/constraints и не подменять production code собственным SQL в «интеграционном» тесте ради зелёного результата.
- Mock допустим на границе внешнего provider/clock/network. Он должен воспроизводить настоящий контракт, включая возвращаемый failed результат. Доменные guards/SQL adapter/transaction, которые исправляются, не мокать в их доказательном тесте.
- Отсутствие, ошибка и неопределённость — разные состояния. Не возвращать `[]`, `null`, `false` как успешную пустоту после неизвестной ошибки; подтверждённый not-found может быть корректным результатом.
- Авторизация проверяет caller, объект и весь набор IDs. Результат предварительной проверки остаётся действительным до commit благодаря согласованной блокировке/version модели.
- Все связанные DB writes используют один tx. Внешний API/native/почта/push не являются частью атомарной DB transaction; нужны явные intents/results и восстановление.
- Массовые UPDATE/DELETE имеют явный scope и проверяемое основание. «Нет в локальном массиве» не основание удалять серверную запись.
- Смена токена сама по себе не завершает прежнюю работу. Каждый async writer имеет owner и revision/epoch; данные разных аккаунтов не делят изменяемый cache namespace.
- Даты хранят смысл. Не прибавлять всегда 24 часа к civil day на DST и не использовать UTC ISO date как локальное «сегодня» без контрактного основания.
- Success UI отражает известное подтверждённое состояние. Оптимистичный UI допустим с pending/rollback/reconciliation, а не с проглоченным failure.
- Не объявлять issue исправленным только по happy path, новому тесту без исходного reproducer или зелёному mock. Не объявлять невозможным conditional issue без проверки его условия.
- При миграции сначала сохранить совместимость и данные, затем переключить readers/writers, проверить переход, затем убрать старое. Release мобильного клиента распространяется не мгновенно.
- Не удалять сомнительные legacy rows/маппинги/credentials автоматически ради прохождения нового UNIQUE. Нужна детерминированная, проверенная политика разрешения конфликтов.
- Не добавлять секреты, реальные токены, email, календарные названия и production dump в commit/evidence. Тестовые данные синтетические; logs содержат безопасные correlation IDs и результаты.
- Не запускать destructive проверки на production. Этот документ не включает обратно cron и не разрешает отправку писем/уведомлений реальным пользователям.
- Для очистки нужны доказательства недостижимости/замены и проверки затронутого поведения. Учитывать динамические импорты, platform entry points, config/plugins, команды сборки/тестов и поддерживаемые upgrade пути. Не объединять семантически разные функции ради снижения числа похожих строк и не смешивать массовую чистку с критическим исправлением.

## 8. Когда и как привлекать человека

Человек нужен для входа в тестовый Apple/Google account, подтверждения письма, системных permissions/Settings, смены timezone и поведения lock screen/background, второго физического устройства, проверки подписанной сборки и продуктовых решений. Он не должен вручную заменять детерминированные SQL/race проверки, которые агент может выполнить в разрешённом test harness.

Минимум для базовых native проверок — один физический iPhone с тестовой сборкой. Для полной проверки межустройственной синхронизации нужны две независимые установки; предпочтительно два реальных iPhone, если текущий канал — iOS. Второе устройство можно предоставить через тестера. При его отсутствии серверный scope проверяется автоматически, но соответствующий двухустройственный device gate остаётся NOT_RUN. Android проверять физически/подписанной сборкой, если этот канал входит в выпуск; успешный iOS сценарий его не закрывает.

Перед обращением к человеку агент готовит рабочий тестовый build, данные, инструмент для безопасного наблюдения, точные шаги и ожидаемый результат. Если нельзя получить сборку/доступ самостоятельно, запросить конкретно недостающий доступ, не просить «просто проверить всё».

Шаблон задания человеку:

> Нужна проверка DEV-XX для finding IDs … . Сборка …, staging …, тестовые аккаунты A/B … . Подготовлены отдельные календари QA-A/QA-B с событиями … . Выполните шаги 1–5 из карточки; ожидаем … . Для результата нужны: время шага, фактический экран/событие и безопасный screenshot без личных данных. После проверки восстановите timezone/permission … . Пока она не выполнена, статус — NOT_RUN, не PASS.

Test-only barriers/fault injection не должны быть доступны в production сборке/роуте. Если сборка содержит искусственную задержку native callback, явно указать её человеку, затем повторить обычный happy path без задержки.

## 9. Миграции, старые пользователи и выпуск

Перед schema/credential/mapping изменениями проверить три набора: пустая БД; существующая корректная схема; намеренно проблемные legacy данные (дубли tokens/providers, unverified email, неизвестные mappings, старые claims, неоднозначные даты). Использовать синтетические fixtures или разрешённую обезличенную копию, не незащищённый production dump.

Зафиксировать backup/restore и recovery plan до опасного изменения. «Откатить бинарник» не всегда откатывает схему/данные. Предпочитать совместимое расширение схемы, отдельный проверяемый backfill, переключение и позднее удаление старого; при невозможности обратного DDL описать forward recovery. Проверить сам restore/recovery на тестовой БД.

Матрица совместимости включает новый backend со старым установленным клиентом, новый клиент с предусмотренной переходной серверной версией и обновление local storage прежнего пользователя. Legacy write с неправильным scope нельзя оставлять опасным ради совместимости: ограничить сервером безопасный scope или вернуть явную необходимость обновления, согласовав UX.

Релиз допускается, когда High сценарии и затрагивающие данные/изоляцию gates прошли в применимых окружениях; условный High IA01 закрыт guard и проверкой deployment конфигурации. Для остающегося NOT_RUN/DEFERRED указать риск и конкретного принимающего решение человека. Не писать «всё вылечено», если отсутствуют проверки устройств, совместимости или миграции.

После согласованного выпуска наблюдать безопасные метрики: auth/refresh failures, conflicts/rollback, sync partial/unknown, orphan cleanup backlog, outbox/claim age, registration failures, receipt errors. Пороги и rollback/disable условия привязать к baseline и конкретному изменению; аудит не измерял production частоты. Включение автоматических reminders выполняется отдельно после R8 и проверки эксплуатационных ограничений.
