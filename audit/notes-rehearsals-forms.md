## DF01 — Medium, условный сценарий — редактирование сдвигает время при разных timezone профиля и устройства

Категория: даты / целостность данных. Условие достижимости: timezone профиля в AuthContext должна отличаться от текущей timezone устройства. Основной аудитор указал, что Auth выполняет автоматическую синхронизацию timezone; при обычном успешном запуске это условие может отсутствовать, поэтому нельзя описывать DF01 как ошибку каждого редактирования. Само расхождение преобразований ниже подтверждено; достижимость несовпадения после смены timezone устройства, сбоя автосинхронизации либо другого изменения профиля требует проверки в Auth/runtime. Ссылки на механизм автосинхронизации добавляет основной аудитор; в этом доборе новые production-файлы не читались.

Цитата `src/features/calendar/hooks/useAddRehearsalForm.ts:153-158`: `const startsAt = new Date(rehearsal.startsAt); ... setDate(startsAt); setStartTime(startsAt); setEndTime(endsAt);`. Экран показывает время через `formatDateToTimeString(form.startTime)` (`AddRehearsalScreen.tsx:220,232`), а этот helper читает device-local `date.getHours()` (`src/shared/utils/time.ts:54-57`). Обратная запись в `useAddRehearsalSubmit.ts:51-65` использует `userTimezone = user?.timezone || 'UTC'` и `dateTimeToISOInTimezone(dateString, startTimeString, userTimezone)`.

Сценарий: timezone устройства UTC, профиля Europe/Moscow. Сервер хранит начало `2026-01-20T15:00:00Z` (18:00 Москвы). Форма редактирования показывает 15:00; пользователь меняет только название. Save интерпретирует 15:00 как Moscow и отправляет `12:00Z`. Репетиция незаметно сдвигается на 3 часа. Для перехода суток может измениться и календарная дата. `time.ts:177-191` подтверждает, что параметр timezone применяется к указанным локальным часам.

Минимальная правка: при заполнении edit преобразовать timestamps в дату и часы user.timezone теми же `isoToDateStringInTimezone/isoToTimeStringInTimezone`, которые применяет `useRehearsals.ts:29-34`. Плюс — небольшой единообразный fix; минус — Date в роли «часов» продолжает быть неоднозначным. Правильное решение: хранить draft как YYYY-MM-DD и HH:mm с явным timezone, создавать Date только для picker, timestamps формировать в одной точке. Плюс — устраняет расхождение чтения и записи; минус — затрагивает handlers и picker adapter. Трудоёмкость: минимум 3–5 часов; правильно 1–2 дня.

Ручная проверка после разрешения запуска: загрузить и сохранить без изменения времени при нескольких парах device/profile timezone; исходные startsAt/endsAt должны сохраняться.

## DF02 — Medium — невозможно удалить всех участников при редактировании

Категория: контракт API / целостность состава участников.

Цитата `src/features/calendar/hooks/useAddRehearsalSubmit.ts:70`: `participant_ids: selectedMemberIds.length > 0 ? selectedMemberIds : undefined`. Этот объект отправляется и при PUT (`:76-81`). Проверяющий сервер подтвердил контракт: PUT с отсутствующим participant_ids сохраняет прежний roster, а переданный `[]` очищает его. Точный server line ref добавляет основной аудитор из своей части D.

Сценарий: открыть репетицию с приглашёнными, снять все флажки и сохранить. JSON не содержит participant_ids, сервер оставляет приглашённых. Экран сообщает успех, однако люди продолжают считаться участниками и видеть репетицию.

Минимум: для edit всегда отправлять selectedMemberIds, включая пустой массив. Плюс — локальный fix; минус — различное поведение create/update остаётся неявным. Правильно: формализовать DTO и семантику «поле отсутствует»/«пустой список», передавать явный массив roster и проверять сохранённый результат. Плюс — предотвращает неоднозначность контрактов; минус — синхронизация client/server tests. Трудоёмкость: минимум 1–2 часа; правильно 0.5–1 день.

Не путать с create: сервер сообщил, что POST без participant_ids не создаёт RSVP, а не приглашает всех. Поэтому этот конкретный finding относится к edit.

## DF03 — Medium — после ошибки загрузки edit доступны сохранение и перезапись неполных данных

Категория: обработка ошибок / целостность данных.

Цитата `src/features/calendar/hooks/useAddRehearsalForm.ts:137-138`: `setLoadingRehearsal(true); setIsEditMode(true);`; catch/finally `:178-182`: `Alert.alert('Error', 'Failed to load rehearsal data'); ... setLoadingRehearsal(false);`. Нет состояния loadError, закрытия формы либо блокировки submit. В `AddRehearsalScreen.tsx:261` disabled равен только `loading || form.loadingRehearsal`.

Сценарий 1: getBatch временно не отвечает. Форма остаётся в editMode с текущими датой/часами и пустыми полями по умолчанию. Пользователь после предупреждения нажимает «Обновить», PUT уходит с исходным rehearsalId, новыми default timestamp и пустыми полями. Серверный аудитор подтвердил, что отсутствующие title/location в PUT превращаются в null, поэтому исходные значения теряются. Сценарий 2: основная запись загрузилась, а getResponses/getMembers падает: поля заполнены частично, состав участников ещё не восстановлен, но сохранение разблокировано.

Минимум: отдельный loadError/loadedSuccessfully и запрет submit до успешного завершения всех запросов, retry либо закрытие формы при ошибке. Плюс — локальный безопасный барьер; минус — больше состояний UI. Правильно: атомарно собирать draft из результата полного запроса, публиковать его в форму только при success; явная state machine loading/ready/error и отдельный retry. Плюс — исключает сохранение частичного draft; минус — рефактор загрузки. Трудоёмкость: минимум 2–4 часа; правильно 1 день.

Тест edit (`useAddRehearsalForm.test.ts:127-217`) проверяет success и пустой список, но не сетевой failure с дальнейшим нажатием Save. После полного добора остальных тел этой suite такой проверки также не найдено.

## DF04 — Medium — ночная репетиция проходит проверку, но конец сериализуется на день начала

Категория: границы дат / валидация.

Цитата `src/features/calendar/hooks/useAddRehearsalForm.ts:67-71`: `const end = new Date(start); end.setHours(end.getHours() + 2);`, та же логика при смене начала `:213-220`. Проверка `useAddRehearsalSubmit.ts:172` сравнивает полные Date: `if (endTime <= startTime)`. Но `:64-65` формирует обе границы с одним `dateString`: `startsAt: dateTimeToISOInTimezone(dateString, startTimeString, userTimezone), endsAt: dateTimeToISOInTimezone(dateString, endTimeString, userTimezone)`.

Сценарий: открыть форму в 23:00 или сдвинуть начало на 23:00, автоматический конец — 01:00 следующего дня. Проверка проходит, поскольку Date конца действительно больше начала. Сериализация отбрасывает дату endTime и отправляет конец 01:00 дня начала, то есть до начала. Возможное проявление — отказ серверной валидации, несмотря на корректно выглядящую форму; если сервер пропускает отрицательную длительность, повреждённый интервал. Само неверное payload подтверждено статически; точный server response должен добавить основной аудитор.

То же представление не умеет сохранить корректный multi-day/24h интервал при edit: форма имеет лишь одну дату. Отдельного UI all-day здесь нет, поэтому не утверждается поломка существующего all-day toggle.

F подтвердил CHECK ends_at>starts_at в init-native-schema.sql:137 и migrate-rehearsals-to-timestamptz.sql:37-39. Rehearsal routes:125-128,190-193 не классифицируют constraint failure как400 и возвращают500. При действующей проверенной схеме это отказ записи, а не сохранение отрицательного интервала.

Минимум: валидировать уже сформированные timestamps и явно запрещать переход суток с понятной ошибкой либо переносить endDate на следующий день при поддержке ночных репетиций. Плюс — предотвращает неверный запрос; минус — запрет ограничит сценарий. Правильно: отдельные start/end date-time с общей timezone и явной поддержкой overnight; conflict-check тоже должен учитывать день. Плюс — корректны длинные интервалы; минус — более широкая форма. Трудоёмкость: минимум 2–4 часа; правильно 1–2 дня.

## DF05 — Medium — поздние ответы и незавершённая загрузка дают неверный состав/проверку конфликтов

Категория: гонки запросов / бизнес-логика.

Цитаты `src/features/calendar/hooks/useRehearsalAvailability.ts:53-58,77`: await getMembersAvailability для captured project/date/ids, затем безусловный `setMemberAvailability(availabilityMap)`; effect `:92-93` не отменяет запрос и не проверяет актуальность. Аналогично `useRehearsalMembers.ts:25-26` — `await projectsAPI.getMembers(project.id); setMembers(response.data.members || [])`, без cleanup/guard, а catch `:27-29` сохраняет предыдущий список. Начало новых загрузок не очищает старые результаты. `AddRehearsalScreen.tsx:261` не учитывает loadingAvailability/loadingMembers при разрешении save.

Сценарий доступности: для даты A участник свободен, запрос A задержался. Пользователь переключается на B, запрос B возвращает busy, затем приходит ответ A и перезаписывает карту. Форма уже показывает B, но проверка конфликтов использует данные A и может сохранить репетицию без предупреждения. Даже без out-of-order достаточно нажать Save после смены даты до завершения запроса: старые timeRanges продолжают использоваться. При сетевой ошибке карта сбрасывается в `{}` (`useRehearsalAvailability.ts:85-86`), а `src/shared/utils/conflictDetection.ts:49-51` пропускает участника без данных как не имеющего конфликтов.

Сценарий состава: быстро сменить P на Q; более поздний ответ P перезаписывает members под Q, и auto-select из `AddRehearsalScreen.tsx:80-88` может выбрать id из P для Q. Это усиливает серверную проблему отсутствия проверки membership participant_ids, отмеченную основным аудитором D01; само нарушение прав не приписывается клиентскому hook.

Минимум: номер поколения запроса/cleanup guard, очистка результатов при смене ключа, блокировать submit до актуальных members/availability либо показывать явное «проверка не завершена». Плюс — небольшой набор правок; минус — lifecycle вручную в двух hooks. Правильно: query-key = projectId/date/sorted memberIds/excludeRehearsalId, отмена/игнорирование старых ответов, явные состояния unknown/error/loaded; проверка conflict только для matching key. Плюс — единая корректная модель; минус — шире затрагивает data hooks. Трудоёмкость: минимум 0.5–1 день; правильно 1–2 дня.

## DF06 — Medium — поздний ответ старого фильтра заменяет репетиции выбранного проекта

Категория: гонка запросов / несоответствие фильтра данным. Стык подтверждён проверяющим display: `src/features/calendar/screens/CalendarScreen.tsx:112-115` вызывает принудительный fetch при изменении фильтра, поэтому подозрение на пропуск нового запроса из-за 15-секундного TTL исключено. Однако `src/features/calendar/hooks/useRehearsals.ts:157-158` без проверки актуальности выполняет `setRehearsals(fetchedRehearsals); prime(responses, stats);`. Дополнительный display-фильтр `CalendarScreen.tsx:185` проверяет только date и не отбрасывает данные прежнего проекта. Строки экрана подтверждены другим аудитором D, этот файл здесь полностью не читался.

Сценарий: запрос «Все проекты» ещё идёт; пользователь выбирает P. Новый принудительный запрос P заканчивается первым и показывает правильные записи. Затем завершается старый запрос и заменяет массив данными всех проектов. На экране остаётся выбранный P, но отображаются чужие для этого фильтра записи; данные RSVP также prime-ятся из старого ответа. Серверное разграничение доступа это не обходит, но пользователь может принять решение по расписанию другого проекта.

Минимум: идентификатор поколения/ключ запроса и игнорирование ответа, не соответствующего текущему фильтру/projects/userTimezone; UI дополнительно фильтрует по projectId. Плюс — локальное устранение гонки; минус — управление запросами вручную. Правильно: query-cache по полному ключу с отменой/инвалидацией устаревших запросов. Плюс — единая модель кеша и загрузки; минус — более широкое изменение data hooks. Трудоёмкость: 3–5 часов / 1 день.

## Добор тестов: значимые ограничения гарантий

- **Время проверяется как тип, а не результат.** `useAddRehearsalSubmit.test.ts:36-41` фиксирует Auth timezone=UTC, а success-create `:247-254` и success-update `:342-348` проверяют startsAt/endsAt лишь через `expect.any(String)`. Ошибочная дата, обратный интервал DF04 и сдвиг DF01 проходят такие assertions. `useAddRehearsalForm.test.ts:179-185` после загрузки edit проверяет location/roster, но не часы; `:342-359` проверяет только, что Date конца больше начала, не итоговые timestamps. Нужные проверки: roundtrip edit без изменения времени, конкретные ISO на полуночи/смене суток, device/profile timezone при достижимом несовпадении.
- **Контракт conflictDetection в mock устарел.** `useAddRehearsalSubmit.test.ts:17` целиком подменяет модуль; `:96-100,168-172` возвращает `fullyBusy/partiallyBusy`, тогда как production `conflictDetection.ts:5-10,72-75` возвращает `busyMembers`. `formatConflictMessage` из того же auto-mocked модуля не получает реалистичного результата; assertion `useAddRehearsalSubmit.test.ts:185-193` требует только текст `Continue anyway?`, поэтому не подтверждает правильные имена конфликтующих участников и отсутствие `undefined` в сообщении. Это ограничение теста, а не доказанный баг production formatter. Нужен хотя бы один тест submit с реальным conflictDetection и полным expected message.
- **Пустой состав проверен только для create.** `useAddRehearsalSubmit.test.ts:535-555` намеренно ожидает undefined при selectedMemberIds=[], используя defaultProps с isEditMode=false; единственный update success `:324-358` не проверяет participant_ids. Поэтому отличие семантики PUT, вызывающее DF02, не покрыто. Нужен update после снятия последнего флажка с проверкой переданного [] и серверного состава.
- **API mock single-project подаёт другой основной формат.** `useRehearsals.test.ts:151-162` для getAll возвращает только startsAt/endsAt. Основной аудитор сервера подтвердил, что реальный getAll возвращает также legacy date/time в timezone пользователя, поэтому production может идти по раннему возврату `useRehearsals.ts:23-24`. Legacy-test `useRehearsals.test.ts:391-418` существует, но подаёт этот формат через getBatch; нет интегрированной проверки реального getAll-контракта с дополнительными RSVP-запросами и timezone. Подмена `isoToDateString/isoToTimeString` в `:31-35` не подменяет реально используемые `...InTimezone` helpers и сама по себе не является доказательством ошибки.
- **Гонки и смена ключа fetch не моделируются.** `useRehearsals.test.ts` целиком содержит отдельные монтирования для all/single/empty, но не переключение фильтра после успешной загрузки, cache window или перекрывающиеся запросы. Test «should clear rehearsals when no projects» `:259-268` стартует сразу с пустым списком и не проверяет очистку прежних данных. В перечисленной директории нет отдельных suites для `useRehearsalMembers`/`useRehearsalAvailability`; охват в иных частях проекта этим не исключается. Нужны deferred promises с порядком завершения B→A и submit при незавершённой availability, соответствующие DF05/DF06.
- **Часть reactivity assertions ничего не различает.** `useTimeRecommendations.test.ts:466-484` добавляет участника без busy-данных и до/после проверяет length=1; `:519-537` меняет date при той же карте доступности и снова проверяет length=1. Старая закешированная выдача прошла бы эти проверки. При этом `:487-516` содержательно проверяет изменение endTime после обновления availability; полную suite нельзя считать фиктивной. Нужен сценарий, где изменение выбранного состава должно менять интервалы, а даты проверять вместе с реальной загрузкой keyed availability.
- **All-day fixture ограничен рабочим окном.** `useTimeRecommendations.test.ts:50-64` под названием «busy all day» использует 09:00–23:00. Он подтверждает отсутствие рабочего окна, но не доказывает обработку 00:00/24:00, all-day flag или multi-day: таких сценариев в этой suite нет. Обычные пересечения, смежные интервалы, минимум один час, обрезка 09:00–23:00, tentative и дробная duration представлены конкретными assertions.
- **Навигационный mock фиксирует вызов, но не существование маршрута.** `useAddRehearsalForm.test.ts:382-401` ожидает ровно `navigate('Projects', { screen: 'CreateProject' })` в jest.fn; не проверяет реальное дерево навигации. Стык H, отмеченный выше, этим тестом не закрывается.

Это пробелы и расхождения тестовых моделей, без самостоятельных новых finding IDs. Исправлять их следует вместе с соответствующей логикой: контрактные assertions и небольшие интегрированные сценарии предпочтительнее проверок, повторяющих текущее выражение production.
