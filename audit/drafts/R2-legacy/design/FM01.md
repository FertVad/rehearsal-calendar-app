# FM01: documented UTC source to instants

## Supported first transition

Proposed predecessor `legacy-utc-date-time-v1`, successor
`modern-instants-retained-utc-source-v1`. This is an explicit source-semantics
profile, not an assertion that every database with date/time columns means UTC.
Inspect each table independently; permit only declared combinations in the
manifest. Other modern tables must still satisfy the chosen domain profile.

- Source columns: `date DATE`, `start_time TIME WITHOUT TIME ZONE`,
  `end_time TIME WITHOUT TIME ZONE`, stable primary keys and the expected
  ownership foreign keys. Wrong types, unknown triggers/RLS, inherited tables,
  custom generated expressions and unreviewed restrictive constraints refuse.
- Targets: both absent, or explicitly nullable TIMESTAMPTZ columns containing
  **only NULLs**. One absent target may be a separately enumerated empty-column
  shape, not automatic inference. Any non-NULL target in either column refuses
  the entire first transition, even when it happens to equal the candidate.
- Availability has an existing BOOLEAN `is_all_day`; NULL is ambiguous and
  refuses. A missing flag needs a separate predecessor for the historical
  00:00/23:59 inference, rather than silently running add-is-all-day-flag.
- Timed rows require finite non-NULL dates, non-NULL times strictly below
  24:00, and end_time > start_time. An interval ending before/equal to its start
  is not silently interpreted as overnight. Source precision is retained in
  SQL; do not convert through JavaScript Date or format to minutes.
- All-day availability requires a finite non-NULL date. Existing start/end
  time values, including NULL or noncanonical values, are retained unchanged;
  under this explicitly selected historical profile the true flag makes them
  ignored for target computation. Count these cases separately in preflight.
- Rehearsals use their timed source interval even if their existing all-day
  flag is true: that matches the historical rehearsal conversion. Preserve the
  flag, do not import availability's special endpoint rule into rehearsals.
- Check candidates are representable by the current runtime timestamp
  serializer. Exotic infinite/out-of-runtime-range source dates are explicit
  unsupported data, not silently clipped. No new application date policy is
  implied by the narrow migration profile.

## Conversion expressions

For rehearsals and timed availability:

```sql
(date + start_time) AT TIME ZONE 'UTC'
(date + end_time)   AT TIME ZONE 'UTC'
```

For all-day availability only:

```sql
(date + TIME '00:00:00') AT TIME ZONE 'UTC'
(date + TIME '23:59:00') AT TIME ZONE 'UTC'
```

`date + time` is a timestamp without zone, and the explicit AT TIME ZONE
interprets that value in the named zone. No implicit `::timestamptz`, session
DATE(timestamptz), user timezone, project timezone or application-process
timezone participates. [PostgreSQL date/time semantics](https://www.postgresql.org/docs/15/functions-datetime.html)

The historical availability file explicitly specifies 23:59:00. The current
client uses 23:59:59.999 for newly saved all-day rows. Do not extend old records
by 59.999 seconds as an incidental timezone repair. Floating civil dates,
inclusive/exclusive ends, cross-midnight intervals and C01 belong to R6.

`fix-date-column-types.sql` is not a dependency to execute blindly. A source
`date TIMESTAMPTZ` is outside this DATE profile. An optional explicit
`legacy-utc-midnight-timestamptz-date-v1` profile could derive
`(date AT TIME ZONE 'UTC')::date` only after proving every source is UTC midnight
and preserving the full original field. Non-midnight or unknown semantics
refuse. Naive timestamp/text/timetz columns require their own reviewed profile;
do not normalize their types in place and discard provenance.

## Atomic preservation and verification

1. Acquire runner/table locks; inspect exact source structure and aggregate
   the data preconditions before any writes. Construct a transaction-local
   typed snapshot keyed by original row ID when useful for comparisons. No
   row values appear in logs. Counts distinguish source rows, timed/all-day,
   target-prefilled/partial, invalid intervals and unsupported dates.
2. Add targets only for an accepted absent-target shape. Populate both from
   the same source snapshot. Never use the old `WHERE starts_at IS NULL` as a
   mixed-state repair; it can overwrite an already-filled ends_at.
3. Compare target instants to the explicit candidate for every source row;
   require zero mismatches, finite/non-NULL instants and ends_at > starts_at.
   For timed rows, `(starts_at AT TIME ZONE 'UTC')::date/time` and the symmetric
   end fields must round-trip exactly. For all-day availability, compare the
   UTC date and prescribed 00:00/23:59 endpoints, not ignored source clocks.
4. Compare original ID sets, row counts, every original field and all related
   rows with the snapshot. No deletion, merge, owner/project/source/external ID
   change, title/notes rewrite or foreign-key relationship change is permitted.
   All-day ignored source clocks must survive exactly as well.
5. Set target NOT NULL, ensure the reviewed valid time-order check and indexes.
   Preserve original date/start_time/end_time columns and values. **Relax only
   their old NOT NULL constraints** in the successor profile: current runtime
   INSERTs provide only starts_at/ends_at. Keeping the old required columns
   would make an apparently successful migration unusable.
6. Verify the explicit successor profile, then record the actual new artifact
   and verified transition in the same transaction. Any preflight, verification,
   DDL, ledger or trigger failure rolls everything back. No drop-old SQL runs.

The retained columns are historical originals, not a dual-write API. Existing
runtime edits may legitimately change starts_at/ends_at while the original
source values stay intact; new runtime rows leave old fields NULL. Thus full
source↔target equality is an immediate migration postcondition, not a perpetual
condition on all future application edits. Applied-history repeat must verify
checksums/structural successor, skip conversion, and never overwrite edited
instants. Do not implement a down migration that reconstructs original clocks
from already-edited targets. Retirement of preserved sources is a separate
reviewed cleanup after a recovery plan exists.

## Already-filled, partial and already-converted data

Without this transition's trusted committed history, any filled starts_at or
ends_at returns `LEGACY_TARGET_ALREADY_POPULATED` with counts only. Partially
filled rows are equally unsupported. A separate read-only reconciliation can
compare preserved sources to the UTC candidate, but equality alone does not
prove historical provenance. The default transition never adjusts values.

If source columns were dropped, no timestamp arithmetic can recover whether
the historic write used UTC, Jerusalem DST or local project time. Current
TimeZone does not prove the original session. A separate approved repair would
need original backup/provenance, a data-specific proposed mapping, before/after
comparison and a recovery route. Neither global +offset nor rerunning the old
conversion is a supported fix.

Proposed stable metadata codes: `LEGACY_TIME_LAYOUT_UNSUPPORTED`,
`SOURCE_SEMANTICS_UNDECLARED`, `LEGACY_TARGET_ALREADY_POPULATED`,
`LEGACY_SOURCE_INVALID`, `LEGACY_INTERVAL_UNSUPPORTED`,
`LEGACY_ROUNDTRIP_MISMATCH`, `LEGACY_SOURCE_CHANGED`. Raw SQL errors, dates,
titles, user IDs and row payloads are not console diagnostics.
