# FM02: repeat-safe email-provider backfill

## Supported transition and invariant

Proposed transition `email-provider-key-and-backfill-v1` accepts an enumerated
modern PostgreSQL users/provider layout, with ordinary existing OAuth identity
uniqueness, expected FK/check constraints and compatible timestamp/metadata
types. A missing provider table can be a separately enumerated predecessor
using the reviewed canonical PostgreSQL DDL; do not execute the SQLite001 file
or its commented production alternative. Unknown/partial table shapes refuse.

At commit: every user whose password_hash is non-NULL and not the empty string
has exactly one email-provider row, and every user has at most one email row.
This eligibility matches the historical backfill's presence test. It does not
prove a hash is valid or a password is known, usable or owned by that user.
Opaque hashes are not rewritten or emitted. Password usability/policy belongs
to A03/A04/R3. A report must not claim the complete credential registry is now
truthful merely because this snapshot condition holds.

Preserve the existing global UNIQUE(provider_type, provider_user_id), its
ordinary NULL behavior, and all OAuth subjects. Add:

```sql
CREATE UNIQUE INDEX native_auth_providers_one_email_per_user
  ON native_auth_providers (user_id)
  WHERE provider_type = 'email';
```

The predicate deliberately includes all email rows, not only rows with a NULL
subject. The supported data profile nevertheless refuses unexpected non-NULL
email subjects until reviewed. Do not add UNIQUE(user_id,provider_type) for all
providers: that would choose an unrelated multiple-OAuth-accounts policy.
Do not add NULLS NOT DISTINCT to the existing global key: it would allow only
one NULL-subject email row across all users.

Backfill with a conflict target that names the actual guarantee:

```sql
INSERT INTO native_auth_providers
  (user_id, provider_type, provider_user_id, provider_email,
   provider_metadata, created_at, updated_at, last_used_at)
SELECT id, 'email', NULL, email, NULL,
       transaction_timestamp(), transaction_timestamp(), NULL
FROM native_users
WHERE password_hash IS NOT NULL AND password_hash <> ''
ON CONFLICT (user_id) WHERE provider_type = 'email' DO NOTHING;
```

This is a design sketch; implementation must schema-qualify reviewed identifiers.
An optional NOT EXISTS can avoid needless attempted inserts/sequence advances,
but is only an optimization; uniqueness plus ON CONFLICT is the concurrency
guarantee. Do not use ON CONFLICT DO NOTHING without a target, which could mask
an unrelated broken constraint. Existing rows receive no UPDATE, including
metadata/email/timestamps. [Partial uniqueness](https://www.postgresql.org/docs/15/indexes-partial.html)
and [ON CONFLICT index inference](https://www.postgresql.org/docs/15/sql-insert.html)
support this narrow conflict target.

New created_at/updated_at mean when the registry record was created, so use the
transaction timestamp. Do not copy nullable user.created_at into provider's NOT
NULL columns, guess when a password was first established, or label a user's
last_login_at as an email-method login (it may be OAuth). New last_used_at and
metadata are NULL. No verified flag/evidence is created or inferred from email
strings, password presence, OAuth metadata or this migration's timestamp.

## Data preflight and concurrency

- Under sorted runner table locks on both native_users and
  native_auth_providers, count duplicate email groups/extra rows, email rows
  with unexpected external subjects, email rows attached to users without a
  nonempty password, and existing non-NULL provider_email mismatches. Supported
  strict profile refuses these inconsistencies unchanged; NULL provider_email
  may remain unknown and is not silently filled. Existing matching email rows
  and users with only OAuth are preserved. Count source values that cannot fit
  the target declaration (for example a users.email longer than the provider's
  varchar(255)); refuse `EMAIL_PROVIDER_SOURCE_UNREPRESENTABLE` rather than
  truncate or normalize an address.
- Validate index **semantics**, not just its name: user_id, email predicate,
  valid/ready/unique/nondeferrable structure, correct table/schema. A same-name
  wrong index is drift. No IF NOT EXISTS shortcut hides it. If the correct key
  exists, validate it and run only the missing-row backfill if this is an
  explicitly selected new backfill, rather than recreating the index.
- Create the ordinary transactional index and insert in the same transaction
  as postconditions/history. Do not use CREATE INDEX CONCURRENTLY inside this
  transaction or suggest its name means concurrent-safe data repair.
- Advisory locking serializes runner peers. SHARE ROW EXCLUSIVE table locks
  also prevent password/provider writes changing the cohort between preflight
  and commit. Bound lock waits and fail/rollback; do not hold an indefinite
  deployment lock while serving writes. These locks are not a guarantee that
  application workflows spanning multiple transactions resume coherently;
  deployment still requires coordination with active writers.
- The unique key independently arbitrates concurrent insert attempts after
  installation, including code that bypasses the migration advisory lock.
  A second runner may return MIGRATION_BUSY, then an explicit retry sees
  committed history and returns unchanged. The routine must never report two
  successful inserts for the same user's email method.

At commit, assert zero eligible users missing an email row, zero duplicate
email groups, exact expected inserted cohort/count, and byte/value equality of
all preexisting provider rows, every users row, OAuth identities, passwords and
token_version. Sequence gaps from conflicts are harmless; row idempotence does
not mean PostgreSQL sequence counters rewind. Committed-history repeat skips
the already-applied backfill and must not re-add a deliberately unlinked row.

## Existing duplicate policy: non-loss is mandatory

Default supported profile: `EMAIL_PROVIDER_DUPLICATES` refuses the entire
transition with counts only. No rows/history/index survive a failure. This
alone is a complete safe policy for ambiguous data, but is not a claim that
existing duplicate production rows were repaired.

If actual data requires consolidation, design a **separate explicit**
`email-provider-exact-duplicates-archive-v1` transition. It may keep the smallest
ID only for rows identical in all other persisted columns, with NULL external
subject and no external references to provider IDs. Before deleting extras,
preserve complete typed originals (including all IDs and exact metadata text)
and the old-to-retained mapping in a protected transactional archive or a
verified restorable snapshot. Verify reconstruction of the complete pre-state,
counts and reference integrity before commit. Do not log that payload.

Different emails, subjects, metadata, timestamps or externally referenced IDs
are not exact duplicates; refuse instead of silently merging/maximizing fields.
A later specific policy can preserve every alternative and explain its chosen
current representation. Archive retention/privacy and restoration must be
specified before implementation; a digest or count alone is not preservation.
No automatic consolidation of OAuth identities or user accounts is in scope.

## FM02 is not A04 or A01

Current auth register inserts only native_users; PUT password updates only
password_hash/token_version. unlink counts provider rows, then separately
deletes by type and can clear password_hash. Backfill does not fix these writers
or the concurrent last-method race. After commit, new password accounts can
again lack a registry row; existing unlink behavior can still drift the model.
The migration's coverage assertion is a locked snapshot, not a forever
invariant and not a reason to replay the backfill at application startup.

R3 must maintain credentials transactionally, lock the user for mutations,
check actual remaining methods, define linking/unlinking and email ownership,
and revoke sessions where required. FM02 never changes password hashes,
token_version, account ownership or verification; no trigger is added as an
unreviewed workaround. Report FM02's supported replay/concurrency repair
separately while A04 remains open.
