## Замечания

### R2-01 — P2: отсечка по дате первого git-коммита не доказывает отсутствие строк, затронутых FM01

**Место:** `audit/REMEDIATION_R2.md:74–77`; `audit/evidence/R2/ops-r2-data.json:15,26`; производный статус — `audit/REMEDIATION_STATUS.md:115`.

Счётчики владельца показывают отсутствие строк с `created_at < 2026-01-17` и NULL. Их достоверность не оспаривается. Но из наличия нового SQL и кода в git от 16.01 не следует, что production уже был конвертирован к этой дате. Строка, созданная **после** отсечки в ещё старой схеме, могла попасть под более поздний запуск конверсии. Это отдельный пробел, помимо уже оговорённого пересохранения клиентом.

**Воспроизведение без production:** на PostgreSQL 15 создать временную таблицу с `created_at`, `date`, `start_time`, `starts_at`; записать `created_at='2026-02-01T00:00Z'`, `date='2026-03-01'`, `start_time='10:00'`. В сессии `Asia/Jerusalem` выполнить старое выражение:

```sql
UPDATE fixture SET starts_at = (date + start_time)::TIMESTAMPTZ;
SELECT count(*) FILTER (
  WHERE created_at < '2026-01-17' OR created_at IS NULL
) AS old_count, min(starts_at) FROM fixture;
```

Независимый прогон получил `old_count=0`, но instant `2026-03-01T08:00:00.000Z`, вместо предполагаемого исходного `10:00Z`. Следовательно, нулевой счётчик сам по себе не обосновывает приведённый вывод. Это **не утверждение о реальной порче production**.

**Что нужно для принятия:** подтвердить верхнюю границу фактической конвертации/перехода production на новый writer и происхождение `created_at`, после чего соотнести счётчик с этой границей; либо честно оставить остаточный вопрос данных открытым. Проверять/сдвигать production-данные автоматически нельзя. Без этого достаточно доказательств для безопасного отказа будущей legacy-конверсии, но недостаточно для утверждения «в production нет строк, которые она могла сдвинуть».
