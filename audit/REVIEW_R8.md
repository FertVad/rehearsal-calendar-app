## R8-01 — P1 — ожидание Expo не ограничено, а транзакция держит репетицию и соединение

**Где:** [pushNotificationService.js:123](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/server/services/notifications/pushNotificationService.js:123), создание клиента :14, чтение квитанций :226; [reminderScheduler.js:224](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/server/services/notifications/reminderScheduler.js:224), транзакция :154 и блокировка :191.

**Клетка: просто × серьёзно. Покрытие правкой причины: неполное.** Обычный сетевой отказ — соединение принято, ответ не завершён — не требует попадания в гонку. Он останавливает оставшиеся напоминания этого прогона и задерживает изменение репетиции другими участниками. Несколько зависших прогонов занимают соединения пула. Это эксплуатационная надёжность, не дополнительная защита аккаунтов.

`new Expo()` используется без ограничивающего транспорта. В установленном `expo-server-sdk@3.15.0`, `build/ExpoClient.js:225`, запрос `node-fetch` не получает ни `signal`, ни `timeout`; последующее чтение тела тоже не ограничено. `retryMinTimeout` — задержка повторов при 429, не срок ответа. Оба await в нашем сервисе ждут до завершения транспорта. `catch` работает для исключения, но молчащий сервер исключения не создаёт.

После постановки отметок планировщик удерживает `FOR SHARE` до завершения этого ожидания. Адаптер [db.js:149](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/server/database/db.js:149) не ставит таймаут транзакции или её SQL. `connectionTimeoutMillis: 2000` ограничивает получение соединения из пула, а не уже выполняющуюся работу. Поэтому фраза отчёта «таймаут … откатывает всё» пока описывает результат уже возникшего исключения; собственного предела сетевого ожидания здесь нет.

**Воспроизведение:** независимая PG-проба `slow-real-expo-sdk`, исходники сервиса и адаптера неизменены. Использован настоящий SDK с `EXPO_BASE_URL`, указывающим только на HTTP-сервер `127.0.0.1`; сервер принимает `/send` и удерживает ответ. Через **8229 мс** вызов всё ещё не завершён; в PG видна **1 idle in transaction**. Независимый `UPDATE native_rehearsals` с диагностическим `statement_timeout='2s'` заканчивается `57014`: его блокирует напоминание. Без этого специально установленного в пробе лимита UPDATE продолжал бы ждать. После разрешения локальному серверу ответить отправка и транзакция завершаются. В одноразовой БД `statement_timeout=0`, `idle_in_transaction_session_timeout=0`; production-настройки не проверялись.

Измеренные 8,2 секунды сами по себе не объявляю недопустимой задержкой: дефект — отсутствие конечного срока, подтверждённое кодом SDK и вызывающего сервиса. При таком же зависании чтения receipts транзакция ещё не открыта, но до новых напоминаний прогон вообще не доходит.

**Исправление причины:** единый ограниченный по времени транспорт для отправки и чтения квитанций, с отменой реального HTTP-запроса и согласованным бюджетом прогона. Не полагаться только на прекращение функции хостингом. При истечении срока отправки результат остаётся неопределённым снаружи, но отметка должна освобождаться для повтора, как при нынешнем транспортном отказе; возможный дубль соответствует принятому контракту. Границы ожидания БД/транзакции должны позволять освободить блокировку. Нужна регрессия с молчащим локальным HTTP-сервером: вызов заканчивается ошибкой, отметок нет, редактор получает строку, следующий прогон доставляет. Подмена Expo функцией, сразу бросающей исключение, этого не доказывает.

## R8-02 — P2 — допустимое время с микросекундами принимается за перенос репетиции

**Где:** [reminderScheduler.js:191](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/server/services/notifications/reminderScheduler.js:191), особенно преобразование параметра :192. Прямой формат `startsAt` сохраняется без ограничения точности в [rehearsalService.js:292](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/server/services/rehearsals/rehearsalService.js:292).

**Клетка: просто × мелко. Покрытие правкой причины: нет для части принимаемых timestamps.** Один корректный POST, без гонки, доступа к БД или серверу. Текущее приложение обычно присылает секунды/миллисекунды; не утверждаю, что оно само генерирует этот payload. Цена — отсутствие напоминания о такой репетиции, исправимое редактированием времени. Нового механизма защиты для исправления не нужно.

PostgreSQL хранит микросекунды, а `pg` возвращает `starts_at` как JavaScript Date с миллисекундами. Параметр `new Date(rehearsal.starts_at).toISOString()` уже потерял остаток. Равенство `starts_at = $2::timestamptz` не выполняется даже без переноса. Код возвращает `moved: true`, и cron успешно заканчивает прогон, никому не напомнив.

**Воспроизведение через настоящее локальное HTTP-приложение на PG:** авторизованный владелец проекта отправляет `POST /api/native/projects/:id/rehearsals`, состав включает активного участника. В `startsAt` — будущее время внутри 12–24 часов с дробью `.123456Z`, в `endsAt` — конец на час позже с той же точностью. Проба `api-submillisecond-start` получила:

```text
POST: 201
startsAt: 2026-10-06T11:17:39.123456Z
stored:   2026-10-06 11:17:39.123456+00
scheduler: ok=true, found.24h=1, told.24h=0
claims: 0
```

Для повторения даты надо сдвинуть относительно текущего времени. Проверка только через прямой SQL не использована как достаточное доказательство: принятие payload подтверждено самим API. Для часового напоминания выполняется тот же `remindRehearsal`, поэтому смена окна проблему не исправляет.

**Исправление причины:** сравнивать сохранённый момент с исходным снимком без потери точности, например передавать из первого SQL отдельное текстовое значение `starts_at` для проверки под блокировкой. Не ослаблять проверку переноса допуском «примерно то же время» и не добавлять особую ветку для шести цифр. Добавить PG-регрессию: принятая через API репетиция с микросекундами напоминается; действительно перенесённая по-прежнему пропускается.

## Проверенные механизмы и границы

| Пункт | Результат |
|---|---|
| GR01: результат по человеку, а не потерянные счётчики | Принято для завершившейся отправки. Хотя бы один принятый токен → `delivered`; ни одного → `undelivered`; нет подходящих токенов/уведомления выключены → `unreachable`, остаётся входящее. У недоставленных удаляются и отметки, и созданные входящие. Ошибка чтения токенов/счётчика не превращается в пустой список. |
| GR02: отметка и входящие одной транзакцией | Принято для исключений/отката. Настоящий PG показывает откат при отказе INSERT входящего. Дополнительно проверен отказ непосредственно COMMIT после принятия пуша — подробности ниже. Зависшее ожидание остаётся R8-01. |
| GR03: статус cron | Принято для перечисленных в контракте отказов: чтение due/receipts, транзакция, недоставка всем устройствам человека, потеря записи тикета. HTTP 500 проверен маршрутом и PG. Отрицательная прочитанная квитанция сама по себе только учитывается/обрабатывается и не делает `ok=false`; это соответствует явному контракту «квитанции только удаляют мёртвые токены», не обещанию повторять доставку по любому receipt error. |
| GR05: перенос | `FOR SHARE` действительно ждёт за переносом, затем проверяет новое время. Два одновременных планировщика ждут один и тот же unique claim и не отправляют дважды. Условия верны при сохранённой точности снимка; R8-02 нарушает её. |
| G02: тикеты и receipts | Таблица заполняется; квитанции читаются после 15 минут; неизвестная до суток ждёт, истёкшая удаляется; DNR удаляет старый токен. Повторная регистрация после записи тикета сохраняется, включая сравнение на PG. Узкая граница регистрации в процессе отправки — ниже. |
| Схема 011 | Принято. В каталоге ровно 22 таблицы; прежняя 21 запись побайтово по JSON-структуре не менялась. Новая таблица, её PK/FK/индекс, bootstrap, inspector, manifest и шаг `--apply` согласованы; R2_SCHEMA/R2_MIGRATIONS прошли в общем PG-прогоне. |
| Дополнение R7, `83facf1` | Принято. Оба fallback используют `localHere`, фильтрующий кэш через общее `current`. На старом `calendarMappings.ts` из `ad09154` ровно два новых теста падают на expect, 8 остальных проходят; на HEAD весь набор зелёный. Когда нельзя прочитать и сервер, и перечень календарей, остаётся явно описанный fallback ко всему кэшу; абсолютной гарантии при двойном отказе код не даёт. Третий круг R7 не открывается. |

**Сбой COMMIT после отправки.** В независимой PG-пробе deferred constraint trigger отклонил COMMIT после принятого тикета. Получено: `ok=false`, отметок **0**, отдельно записанных тикетов **1**. После удаления диагностического триггера повтор прошёл: всего **2 отправки**, **1 отметка**, входящие первого откатившегося вызова не фиксируются. Это реальная проверка заявленного компромисса, а не вывод только из SQLite.

**Остановка процесса.** Незакоммиченная отметка не становится вечной записью: при разрыве соединения PostgreSQL откатывает транзакцию. Завершение процесса на Vercel и время освобождения его соединений здесь не измерялись, это DEV-14. При просто зависшем, но живом процессе разрыв ещё не произошёл — поэтому R8-01 существенен для замены отдельной аренды транзакцией.

**Смысл «хотя бы один раз».** Здесь он ограничен принятием хотя бы одного сообщения Expo либо зафиксированным входящим при недоступных устройствах. Это не обещание показа push на телефоне. Повтор возможен при следующем работающем прогоне, пока репетиция ещё в соответствующем окне: 12–24 часа или от текущего момента до часа. Постоянный отказ до выхода из окна не превращается в гарантированную позднюю доставку. Эти границы не требуют нового класса очередей для нынешней задачи.

**Цена транзакции и Vercel.** Во время запроса Expo один клиент пула удерживается; `recordTickets` дополнительно получает другой клиент вне транзакции. У адаптера максимум 10 и ограничение ожидания выдачи клиента 2 секунды. При двух планировщиках это допустимая цена простой модели, но предел выдачи клиента не ограничивает сетевую операцию на уже занятом клиенте. Без R8-01 медленный внешний сервис задерживает также правку репетиции и следующих получателей. Фактическую конфигурацию длительности функций Vercel не читал; в локальном `vercel.json` собственного `maxDuration` нет.

**Порядок выкладки.** Миграция 011 нужна до новой версии сервера, даже при отключённом расписании: таблицу использует общая служба отправки. Независимая проба временно переименовала таблицу в одноразовой БД: пуш принят, отметка остаётся, `ok=false`, ошибки шагов `receipts` и `24h`. Это соответствует отчёту. Отсутствие таблицы вызывает ошибку чтения receipts даже в прогоне без новых отправок. Ни миграции, ни включение напоминаний, ни production smoke не выполнялись.

## Ниже планки — строки для known-issues, не отдельный круг

**Регистрация токена во время отправки. Клетка: особое стечение × мелко. Покрытие: частичное.** [pushNotificationService.js:166](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/server/services/notifications/pushNotificationService.js:166) снимает `created_at` после ответа Expo, сразу для накопленных тикетов. Регистрация между началом отправки и записью тикета старше этого `created_at` и потому не защищена условием :191. В локальной PG-пробе `last_active_at=16:17:30.394`, тикет `16:17:38.618`; поздний DNR удалил повторно зарегистрированный токен (`tokensRemaining=0`). По планке владельца это не блокирует приёмку.

Предлагаемая строка: «Поздний DeviceNotRegistered может удалить токен, повторно зарегистрированный пока предыдущая отправка ещё ожидала ответ Expo: границей пока служит время записи тикета. Следующая успешная регистрация устройства восстановит токен». Если уточнять существующий механизм, ему нужна отметка времени/поколения отправляемого токена, снятая до ожидания ответа, а не ещё одна очередь.

Покрытие: отложено в общую транзакцию правки №10.** Указанное в `known-issues.md` окно между UPDATE времени и отдельным DELETE отметок действительно остаётся. Новый планировщик защищает свою операцию, но не превращает эти два запроса редактора в один. Оставить существующую запись; дублировать находку не нужно.
