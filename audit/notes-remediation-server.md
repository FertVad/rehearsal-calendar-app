Завершённость означает одновременно: инвариант закреплён кодом/БД; старые данные приведены в допустимое состояние; текущий и ещё поддерживаемый клиент понимают новый контракт; отрицательные и конкурентные сценарии проверены через production handlers; последствия внешних систем проверены отдельно; сценарий отката не возвращает уязвимое поведение.

## 2. Порядок работ и зависимости

Каждый шаг — самостоятельный reviewable пакет с картой ID→инвариант→проверки→миграция→откат. Большой рефакторинг всего сервера одним изменением не нужен.

1. **Зафиксировать контракт выпуска и ограничить известные опасные пути.** Определить поддерживаемый DB engine, минимальный совместимый клиент, действующие auth providers, политику legacy accounts и статус reminders. Нельзя автоматически включать расписание: на финальном аудированном HEAD schedule выключен, внешний cron независимо не проверен. H01, A02 и fail-closed IA01 можно исправлять независимым небольшим пакетом, не ожидая всей schema работы. Для A01 краткосрочная мера — не автопривязывать OAuth к неподтверждённому password account; это containment, не законченный email flow. Если полный flow ещё не готов, регистрация должна честно быть недоступной/ограниченной, а не выдавать обычную сессию по недоказанному адресу.
2. **Сначала достоверная DB/test основа.** Устранить F01/F02, определить отказ от неработающего SQLite fallback либо отдельную реально поддерживаемую SQLite реализацию, исправить F05. Сделать reproducible clean provision/upgrade и реальные PostgreSQL integration fixtures. Дальнейшие claims о транзакциях опираются именно на эту основу. Никаких baseline «все файлы уже выполнены» по одному факту существования БД.
3. **Расширить схему без разрушения старого клиента.** Добавить структуры, необходимые для email proof/credential state, operation idempotency, schedule revisions, outbox/delivery attempts и ownership generation. Не обязательно вводить все таблицы сразу: каждая появляется перед своим consumer, с явно проверенными constraints. Пока old/new server одновременно работают, определить безопасный смешанный режим или исключить такую одновременность. Старый writer не должен снова создавать недопустимые строки.
4. **Полный auth recovery/link flow A01/A04.** Включает endpoints, middleware, почтовую доставку, клиентские состояния, legacy reconciliation и отзыв старых сессий. Не считать готовым по unit tests mail helper. Безопасный прямой запрет unsafe auto-link из шага 1 сохраняется до полного ввода этой модели.
5. **Общая authorization policy и атомарный lifecycle.** D01/D02 guards и ограничения B03/B04 можно закрыть раньше полных транзакционных сервисов, но финальная гарантия требует общего locking/order с B01/B02/D03. Create/edit/remove-member/delete-project проходят единый unit-of-work; derived busy slots и outbox записываются там же. Недопустимое состояние не «исправляется потом» обычным клиентским refresh.
6. **Восстановить существующие данные и закрепить ограничения.** Предварительный профиль данных нужен до шага 3, применяемый backfill/cleanup — после появления безопасных writers и до обязательного чтения новой схемы. Сначала выбрать правила, подготовить сверяемую выборку изменений, затем применить контролируемыми партиями. Только после этого включать constraints/read paths, требующие полного backfill.
7. **Push ownership G01 и доставка G02/GR.** Правильная ownership migration требует клиентского протокола сессии/устройства; новая очередь использует outbox шага 5. Внедрять поэтапно: явный result contract → идемпотентный inbox → leases/revisions → tickets/receipts → операционная отчётность. Нельзя оживлять reminders лишь после исправления HTTP200: ошибки claims/delivery тоже должны быть закрыты.
8. **Совместимость, устройства, ограниченный выпуск.** Пройти матрицу ниже, выполнить staging migration rehearsal/restore и сравнение old/new contracts. Ответственный человек принимает результаты auth/письма/device push и решение о возобновлении/стоимости reminders. После ограниченного выпуска — наблюдение, затем остальной rollout. Удаление legacy полей и старых routes — отдельный поздний contract-шаг.

Независимые рабочие ветки после общей фиксации контрактов: admin DOM/CSP; async error/validation boundary; схема/adapter/harness; auth flow; rehearsal policy/lifecycle. Владельцы этих веток согласуют общий migration порядок, error DTO и transaction API до изменений. Delivery не должна создавать собственную несовместимую модель revisions/recipients параллельно lifecycle.

Для этих гарантий достаточно согласованной модели в существующем сервере и PostgreSQL outbox. Не вводить Kafka, новый auth framework или полную замену ORM/сервера без отдельного доказанного требования. Поддержку SQLite можно прекратить только явным продуктовым/эксплуатационным решением; до него честно сохранять статус непроверенного/неработающего обещанного режима, не подменять его тестовым harness.

## 3. A01: полноценное доказательство email, linking и восстановление

### Новые регистрации

- Регистрация создаёт pending challenge/registration с конечным сроком и лимитами, не полноценную рабочую сессию. Не допускать бессрочной блокировки адреса чужой pending регистрацией: resend/restart/expiry и восстановление владельцем адреса должны быть определены.
- Proof привязан к назначению, subject/registration, каноническому адресу, generation и expiry. Секрет токена не хранится/не логируется открытым текстом; одноразовое потребление обеспечивается условным изменением в транзакции, а не проверкой перед отдельным UPDATE. Проверка срока выполняется сервером. Проверка email и password reset/link — разные purposes; общий механизм криптографии не делает токены взаимозаменяемыми.
- Успешная проверка в одной транзакции активирует доказанный credential, фиксирует used challenge и необходимое состояние сессий/registry. Рабочий access/refresh выдаётся только после commit. Потерянный ответ на подтверждение должен иметь понятный recovery: показать уже подтверждённое состояние и дать обычный вход, не обходить одноразовость.
- Resend имеет явное правило поколений: какую ссылку ещё можно открыть и какая уже недействительна. Повторные/поздние mail deliveries не должны неожиданно подтверждать другой email или более старый запрос. Expiry, rate limit и delivery error имеют безопасные пользовательские состояния без раскрытия существования чужого аккаунта.
- SMTP/почтовый API не вызывается внутри долгой DB-транзакции. Транзакционно сохранить намерение письма, затем выполнить доставку с контролируемым retry. Не считать «добавлен helper» эквивалентом рабочего end-to-end подтверждения.

### OAuth и linking

- OAuth sign-in идентифицирует уже привязанный аккаунт по `(provider, providerSubject)`, не по введённому клиентом email. Provider token должен пройти signature/issuer/audience/expiry; IA01 закрывается отсутствием permissive defaults. Для нужных native/web/service audiences — явный allowlist с валидацией при старте/развёртывании. Реальные production env в аудите не проверялись: задача включает проверку наличия настройки, без публикации её значений.
- Наличие verified email в новом OAuth token не доказывает владение password credential, которым кто-то ранее зарегистрировал такой адрес. Для обычного linking нужна свежая аутентификация существующего аккаунта и proof нового provider; link token связан с этой сессией, intent и конкретным provider. Нельзя бесшумно объединить аккаунты по одному совпавшему адресу.
- Для legitimate owner, пришедшего через OAuth на ранее занятую неподтверждённую запись, нужен отдельный recovery/reclaim flow. Proof адреса/провайдера, решение о доверии старым credentials и судьбе старых данных должны быть явными. При восстановлении нельзя сохранить пароль атакующего или его access/refresh: отзывать их в той же атомарной операции, например через установленный механизм версии сессий. Простое очищение password_hash недостаточно.
- Credential registry и реальные usable credentials имеют один источник истины/проверяемое соответствие. Пароль без registry row, ghost provider и email-provider с неподходящей nullability — объекты миграции. Два unlink/change-password/recovery должны сериализоваться на аккаунте: после commit остаётся хотя бы один допустимый способ входа, если операция не является полным удалением аккаунта.

### Legacy accounts и необходимое человеческое решение

Возраст аккаунта, наличие password_hash, старой email-provider row или рабочей сессии сами по себе не являются доказательством владения email. Не проставлять legacy email_verified=true массово. Классифицировать: есть доказанный provider subject/verified proof; есть только неподтверждённый пароль; несколько способов с возможной исторической коллизией; противоречивые/дублированные identity records. Отдельно описать UX для каждого класса.

Для неоднозначных коллизий нельзя автоматически приписывать проекты/персональные данные тому, кто первым подтвердил адрес сейчас, либо удалять чужой credential без согласованного recovery policy. Подготовить отчёт без секретов, карантин спорного linking и процедуру подтверждения/ручной поддержки. У человека должны быть понятные варианты восстановления и уведомление об отзыве способов входа. Решение о массовой повторной проверке/ревокации и сохранении данных принимает ответственный владелец продукта/эксплуатации; агент готовит конкретную выборку и последствия заранее.

## 4. Права и атомарный жизненный цикл

Единая policy функция/сервис отвечает отдельно на canView, canSeeRoster, canRespond, canEdit, canManageMembers. Project admin и invited member имеют разные основания доступа; роль в выбранном клиентом проекте не заменяет проверку запрошенного rehearsal. Не менять специально различавшиеся batch «моё расписание» и admin edit lookup только ради одинаковой выдачи: editor получает разрешённый объект через подходящий контракт.

Для D01 валидировать весь roster до первой записи: тип, допустимые положительные IDs, уникальность, предел размера и полное соответствие активным участникам проекта. Не отбрасывать недопустимые IDs молча с success. Для D02 обычный respond обновляет существующее разрешённое приглашение, а не создаёт новое; административное self-enrol, если продукт его действительно требует, — явно отдельное право и операция. Правила read-by-id, getResponses и respond обязаны совпадать по invitation boundary.

Проверка membership и mutation выполняются в одной согласованной транзакционной модели, сериализуемой с remove-member/role-change. Одного SELECT перед BEGIN или «обернули два запроса в transaction» недостаточно для гонки над отсутствующей строкой. Выбрать общий порядок блокировок project→rehearsal→membership/roster→derived rows, документировать конфликты, при необходимости использовать общий project-level serialization guard для отсутствующих memberships. Все lifecycle writers обязаны соблюдать выбранный протокол; ограниченный retry deadlock/serialization повторяет целую операцию с её idempotency key.

Unit-of-work включает исходную сущность, roster, derived rehearsal busy, schedule revision, отмену старых задач и запись outbox. Helpers получают scoped transaction connection; случайный вызов global db из callback запрещён проверкой/тестом. Внешние email/push/calendar операции не держат DB locks и не выполняются до commit. После commit durable worker выполняет outbox; падение процесса между commit и dispatch не теряет событие.

Повтор create использует ключ, scoped по actor+operation, и проверяет соответствие payload; тот же ключ с другим содержимым — понятный конфликт. Повтор delete/remove-member завершает предусмотренный cleanup либо отвечает однозначным already-complete; временная ошибка после первой части не должна превращаться в вечный 404 с остатками. Для roster update сохранить различие omitted=сохранить, []=очистить; изменить контракт можно только с согласованной совместимостью клиентских форм. Защитить от lost updates revision/expected-version либо документированным сериализуемым overwrite, включая manual availability одного user/day.

Исторические orphaned response/busy rows не доверять как доказательству доступа или списка адресатов. После исправления writers восстановить derived записи из авторитетных rehearsal+membership+roster данных. Не стирать manual/imported занятость при этой реконструкции. Для будущей доставки проверять актуальные права/recipient revision; queued message старому участнику после revoke должен быть отменён. Уже переданный внешнему provider push отозвать гарантированно нельзя — это ограничение явно отражается в release/device проверках и тексте обещаний.

## 5. Схема, миграции и upgrade существующих данных

Предпочтительная минимальная поддерживаемая серверная платформа для исправления — PostgreSQL, поскольку текущие SQL consumers зависят от него. Если SQLite нужен продукту, он получает собственные schema/adapter/integration гарантии. Тестовый перевод SQL SQLite не является проверкой PostgreSQL и не заменяет production SQLite adapter. При явно настроенном недоступном PostgreSQL startup должен отказать; скрытый переход на локальную БД недопустим.

Перед миграцией оператор/агент с отдельной авторизацией собирает read-only schema/ledger профиль, количество потенциальных дублей/орфанов и версии приложения. Проблемные production значения/PII не копировать в отчёты; достаточно агрегатов, безопасных ID и правил отбора. Текущий аудит не проверял live catalog, поэтому нельзя считать production уже сломанным F01/F02 или автоматически переприменять все SQL.

Требования к пути миграций:

- Исполнимый bootstrap для выбранного engine и каноническая схема имеют те же postconditions, что последовательный upgrade поддерживаемой старой версии. Проверяются все обязательные unique/FK/check/index, в том числе availability conflict target F02 и notification indexes; SELECT1 health недостаточно.
- Ledger фиксирует конкретную версию и checksum успешно завершённой миграции. Миграционный lock исключает двух runners. Поддерживаемый DDL и запись ledger атомарны; неизбежные non-transactional операции имеют отдельные стадии и проверяемое восстановление, а не притворную атомарность.
- Dry run не создаёт БД/ledger и ничего не записывает. Baseline допустим только для явно заданной уже подтверждённой схемы/версии; при drift отказывает. Не переименовывать/переписывать уже применённые исторические migrations для «починки» живой БД: добавлять forward repair и сверку.
- Перед unique constraint определить правило каждой категории дублей. Идентичные импортированные события можно свернуть по согласованной identity; конфликтующие длительности/владельцы/credentials нельзя произвольно выбирать по минимальному ID. Push tokens с несколькими владельцами лучше временно лишить спорной доставки и запросить новую корректную регистрацию, чем угадать владельца по ненадёжному timestamp.
- При преобразовании исторических timestamps хранить источник и timezone assumption, проверить образцы на UTC и non-UTC session settings, DST и date-only. Если исходное значение неоднозначно, не делать необратимую «коррекцию» без решения владельца данных. Backfill идемпотентен и возобновляем, имеет счётчики изменённых/неоднозначных/пропущенных строк.
- Сначала expand→совместимые writers→backfill→validate→новые readers→enforce; contract/drop — после прекращения старых writers. Атомарное уникальное владение токеном G01 требует constraint, не только application transaction.

До выпуска — rehearsal миграции на обезличенной репрезентативной копии и проверка восстановления из backup в отдельной среде. Не использовать production backup restore как обычный откат кода после новых пользовательских записей: это теряет новые данные. Для исправимых дефектов предпочтителен совместимый rollback binary/feature или forward repair; необратимая миграция требует согласованного stop-write окна, сохранения новых записей и человеческого решения о восстановлении.

## 6. Push ownership, outbox и reminders

### G01: одного UNIQUE недостаточно для поздней старой сессии

Добавить атомарную уникальность владельца device token и operation, которая передаёт владение единой записью. Одновременно определить installation/registration identity и серверно проверяемое поколение владения. Запрос со старым expected generation или отозванной сессией не вправе «стать последним» после входа B. **Проверять право и актуальность сессии именно для этой installation при commit/атомарном изменении binding**, а не только в auth middleware до ожиданий: A мог пройти middleware, затем выйти, пока B уже получил владение. Глобально ещё валидный access token A на другом устройстве не разрешает ему перехватить binding B. Просто клиентский счётчик или правило последнего arrived request не является достаточным доказательством актуальности. Registration, token rotation и unregister используют один протокол; старый unregister/receipt cleanup не удаляет новую binding. Граница подтверждается совместно клиентом и сервером — только server unique не закрывает весь G01.

### Состояния доставки и GR01–GR03

Outbox identity отделена от transport attempt. Бизнес-событие имеет стабильный ID; inbox имеет unique(event,recipient), а push — per-recipient/per-current-device attempts. Один recipient с двумя устройствами допускает два push по продуктовой политике, но одна успешная попытка не маскирует ошибку другой. Localized wrapper сохраняет structured outcome и конкретных failed/accepted/skipped recipients, не превращает `{failed: N}` в resolved success.

Worker атомарно получает ограниченную lease с attempt/owner и сроком. Только обладатель актуальной lease завершает/освобождает её; старое завершение после lease expiry не изменяет новую попытку. Отказ до dispatch, между двумя claims, timeout и остановка процесса восстановимы. Retry bounded по времени/числу, с backoff; постоянные failures не крутятся бесконечно. Отсутствие token, пользовательский opt-out и известный transport failure — разные состояния. Inbox может быть успешно создан при выключенном push, это не ошибка.

Сохранять ticket ID и связь с attempt/token generation, затем обрабатывать receipts. Accepted ticket означает принятие Expo; положительный receipt — результат передачи провайдеру, не доказательство отображения/прочтения на устройстве. Поздний DeviceNotRegistered обрабатывает точную binding без повреждения нового владельца. Операционная терминология и метрики должны различать эти стадии.

DB transaction не делает внешнюю отправку exactly-once. Если provider принял сообщение, а процесс остановился до фиксации результата, outcome неизвестен. Явно выбрать политику ограниченного повторения с возможным дублем против риска пропуска, применить поддерживаемую provider idempotency при наличии; без неё не обещать отсутствие всех дублей. Логический inbox при этом остаётся идемпотентным. Это обязательный операторский сценарий, а не исключение, скрытое catch.

### GR05: версия расписания и отмена устаревшего

Reminder identity включает rehearsal, recipient, reminder kind и schedule revision. Перенос/изменение roster/deletion меняют релевантную revision и отменяют старые pending задачи в lifecycle транзакции. Claim создаётся условно только для актуальной revision; старый read→move→claim отвергается. Перед внешним dispatch перепроверяется валидность задачи/получателя; неизбежный in-flight transport после dispatch учитывается как ограничение внешней системы, не блокирует новое корректное напоминание новой revision.

Время due считается по instants с управляемыми часами, текст — по реальному startsAt/recipient timezone. Catch-up за 10 минут не называется «через час», та же календарная дата не называется «завтра». Принятую политику all-day/overdue/catch-up описать до изменения scheduler; не добавлять скрытую отправку всем пропущенным историческим событиям во время миграции.

Legacy claims имеют неизвестную семантику доставки: timestamp не доказывает её. Не объявлять все старые claims sent и не удалять их массово ради полного replay. Выделить старые/завершившиеся окна, переносить известные состояния; для ещё актуальных неоднозначных задач определить ограниченную политику catch-up/duplicate risk с ответственным человеком. Scheduler возвращает per-window outcome, failures и incomplete state; route/workflow/monitor отличают пустую выборку от отказа БД/частичной доставки. Возобновление расписания — отдельное осознанное действие после тестов и оценки бюджета.

## 7. Проверки, которые доказывают исправления

В изолированном test environment использовать настоящие production routes/middleware/services и настоящий production PostgreSQL adapter с миграциями продукта. Внешние провайдеры заменяются управляемыми boundary fakes; policy, transaction, roster, notification/result wrappers не подменяются произвольным throw или заранее правильным ответом. Проверять HTTP + состояние всех связанных таблиц + outbox/transport events. SQLite/custom SQL в тесте может быть вспомогательным тестом, но не evidence для основного контракта.

Для гонок нужны два независимых соединения/запроса, барьеры в точках чтения/commit/dispatch и фиксируемая последовательность. Sleep и повтор теста много раз не заменяют воспроизводимое interleaving. После каждого injected failure снять snapshot связанных данных; проверять и запрещённые побочные эффекты, а не только status. Test hooks должны быть недоступны в production build/config. Управляемые часы применяются для expiry/leases/reminder windows; оставлять их запущенными относительно wall clock недостаточно.

## 8. Живые устройства и участие человека

1. **Письма/восстановление:** тестовые реальные почтовые ящики, включая задержку/дубликат письма, открытие ссылки в системном браузере/приложении, уже использованную и просроченную ссылку. Человек должен завершить понятный first registration→proof→login, resend, OAuth collision recovery и отказ старого пароля/сессии. Delivery accepted не доказывает получение письма; проверить папки/фактическое получение. Не использовать ящики реальных пользователей без отдельного разрешения.
2. **Apple/Google:** реальное тестовое приложение с правильными audiences и controlled accounts; неверный audience проверять безопасными test fixtures/отдельной тестовой конфигурацией. Отсутствие production env не моделировать удалением production secret. Людям понятно, какой credential привязывается/отзывается; неоднозначные legacy case проходят согласованную поддержку.
3. **Push и аккаунты:** физические iOS и Android, минимум два тестовых пользователя с общим и несвязанным проектами. На одном устройстве A→logout→B при медленной сети и незавершённой регистрации; на втором — отправитель/контрольный получатель. Проверить lock-screen content, foreground/background/закрытое приложение, token rotation/reinstall, opt-out, несколько устройств на пользователя, tap→корректный объект/отказ доступа. Устройство B не получает новые приватные события A. Уже доставленные системные уведомления и внешние in-flight отдельно сверить с клиентской политикой очистки.
4. **Reminders:** изолированные тестовые события, перенос через границы windows, удаление/снятие участника после постановки задачи, краткий отказ провайдера/worker restart, нейтральный/точный текст времени. Письменно сверить app inbox, ticket/receipt и наблюдение на устройстве — это разные доказательства. Показ push зависит от OS/focus/permission, отсутствие баннера само по себе не делает server state failed.
5. **Admin:** человек открывает staged users/reports с подготовленными безопасными HTML markers, проверяет буквы/кавычки/переводы и реальные статусные действия; убедиться, что строгий CSP не отключил штатные кнопки. Никаких настоящих атакующих payload, чужих токенов или production обращений для проверки.
6. **Эксплуатация/владелец продукта:** подтверждает legacy recovery policy, допустимое воздействие на сессии, план миграции/restore, совместимость старого клиента, метрики и budget. Reminders включаются только после отдельного решения; сама документация плана их не включает.

## 9. Откат и критерии выпуска

Держать отдельные обратимые feature switches для новых writers/readers и фоновой доставки; они не должны выключать fail-closed auth/authorization или позволять старому XSS sink вернуться. Rollback к старому unsafe binary не является допустимым восстановлением сервиса: при необходимости ограничить уязвимый вход/операцию и сделать forward fix. Перед rollback проверить, что предыдущий безопасный binary умеет читать расширенную схему и не испортит backfilled данные. Отзыв credentials/session version и уже выполненные внешние отправки не «откатывать» по умолчанию.

Операционный минимум после выпуска: частоты auth/recovery failures и завершений proof, rejected unauthorized roster/RSVP, transaction/retry failures, schema readiness, очередь/возраст outbox, expired leases, transport accepted/failed/unknown, receipt errors, last complete reminder run и стоимость фоновой работы. Метрики не содержат passwords, JWT, mail proofs, полного push token или личного содержания. Порог остановки rollout задаётся заранее по новой ошибке/росту очереди/расхождению invariants; нельзя ждать только жалоб пользователей.

Для закрытия каждого серверного блока приложить: точные исправленные ID и новые инварианты; schema/API изменения; test evidence с реальным окружением и известными исключениями; результат data reconciliation с агрегатами; подтверждение живых сценариев ответственным человеком; совместимость и reversible rollout/rollback решение. Если device/real-PG/migration rehearsal пока не выполнены, пакет помечается **«реализован, не готов к выпуску»**, а не «исправлено и проверено».
