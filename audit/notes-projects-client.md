## BC01 — Medium — проекты и выбранный проект переживают смену аккаунта

Категория: изоляция состояния / конфиденциальность локальных данных.

Код `src/contexts/ProjectContext.tsx:26-40,66-70`: `if (!user) return;`, `setProjects(projectsList);`, `if (!selectedProject && projectsList.length > 0) { setSelectedProject(projectsList[0]); }`; effect выполняет загрузку только при `user`, не очищая старое состояние при logout. `App.tsx:33-40` держит ProjectProvider выше Navigation, поэтому смена auth-экрана его не размонтирует. Запрос также не связан с идентификатором текущей сессии и не отменяется при её смене.

Сценарий: A выбирает свой проект → выходит → на том же устройстве входит B. `selectedProject` остаётся объектом A даже после успешной загрузки списка B. Открытие формы создания репетиции без projectId берёт этот объект: `src/features/calendar/hooks/useAddRehearsalForm.ts:75-76` — `selectedProject?.is_admin ? selectedProject : null`; effect `:112-128` не проверяет наличие выбранного id в новом списке. Дополнительно поздний ответ запроса A может перезаписать уже загруженный список B, показывая названия, описания и inviteCode A в карточках (`ProjectsScreen.tsx:103,116-117,144-153`). Это не подтверждает обход серверной авторизации, но нарушает разделение клиентских данных.

Минимум: очищать projects, selectedProject и error при смене user.id; игнорировать результаты запроса, если сменился id/номер сессии. Плюс — небольшая правка; минус — отдельный ручной lifecycle. Правильно: кеш и запросы с ключом user.id, отмена/инвалидация на logout, выбор проекта только из актуального списка. Плюс — устраняет весь класс переходов; минус — шире затрагивает context и consumers. Трудоёмкость: минимум 3–5 часов; правильно 1–2 дня с проверками login/logout и гонок.

## BC02 — Medium — после удаления или изменения прав выбранный проект остаётся старым объектом

Категория: целостность клиентского состояния / бизнес-логика.

Код `src/contexts/ProjectContext.tsx:34-40` заменяет `projects`, но обновляет selection только когда он уже null. `src/features/projects/screens/ProjectDetailScreen.tsx:303-309`: `await projectsAPI.deleteProject(projectId); await refreshProjects(); navigation.replace('ProjectsMain');`.

Сценарий: выбрать администрируемый P, удалить его, затем открыть создание репетиции при наличии другого проекта Q. Список уже не содержит P, однако context и форма продолжают использовать P (`useAddRehearsalForm.ts:75-76,112-128`). Аналогично после отзыва admin новая запись списка имеет is_admin=false, а selectedProject хранит старое true. Пользователь видит удалённый проект или недоступные действия и получает отказ API; автоматического перехода на действующий проект не происходит.

Минимум: после каждого fetch функционально сопоставлять selection.id со свежим projectsList, заменять объект актуальным, иначе выбирать первый доступный/null. Плюс — небольшое централизованное исправление; минус — потребители с собственными копиями selection тоже нуждаются в синхронизации. Правильно: хранить selectedProjectId и вычислять объект по текущему списку, сбрасывать выбор и кеш форм при удалении/утрате доступа. Плюс — предотвращает устаревшие поля; минус — изменение контракта context. Трудоёмкость: минимум 2–4 часа; правильно 1 день.

## BC03 — Low — прошедшие репетиции теряют название

Категория: UI / расхождение с заявленной логикой.

Код `src/features/projects/screens/ProjectDetailScreen.tsx:465-468` прямо поясняет, что `scene` устарел, и для будущих записей использует `{rehearsal.title || rehearsal.scene || t.calendar.rehearsal}`. Для прошлых `:525-526` осталось `{rehearsal.scene || t.calendar.rehearsal}`.

Сценарий: запись имеет title «Акт II», scene пустое, date раньше сегодня. В списке прошлых её название становится общим «Репетиция», тогда как до смены даты выводилось настоящее название. Пользователю трудно найти нужную репетицию.

Минимум: тот же fallback с title в строке 526. Плюс — минимальная правка; минус — дублированное выражение остаётся. Правильно: единый renderer/функция получения названия для обеих секций. Плюс — исключает расхождения; минус — чуть более широкая правка. Трудоёмкость: 15–30 минут / 1–2 часа соответственно.

## BC04 — закрытая сверка: date-only объединён с CC01, отсутствие legacy полей опровергнуто

**Окончательная классификация:** D полностью проверил serializer `server/services/rehearsals/rehearsalService.js:228–243`: date/time/endTime возвращаются, поэтому гипотеза ниже о скрытии всех карточек из-за undefined **опровергнута**. Отображение date-only через new Date в UTC− подтверждено и включается в общую CC01 вместе с DP03; отдельного BC04/count нет. Ниже сохранён исходный ход проверки для прозрачности.

Код `src/features/projects/screens/ProjectDetailScreen.tsx:62-67`: `const date = new Date(dateStr); date.toLocaleDateString(...)`. Если API возвращает YYYY-MM-DD, стандартное UTC-прочтение date-only и локальное форматирование в UTC− показывают предыдущий день (2026-09-06 → 5 сентября). Минимум при таком контракте — имеющийся `parseDateString` (`src/shared/utils/time.ts:1-13`).

Более существенная потенциальная несогласованность: `ProjectDetailScreen.tsx:109,183-193,473-474,531` без преобразования читает `date/time/endTime`, тогда как `src/features/calendar/hooks/useRehearsals.ts:16-34` явно преобразует новую форму `startsAt/endsAt` в legacy date/time в timezone пользователя. Если getAll отдаёт только startsAt/endsAt, оба фильтра `undefined >= today` и `undefined < today` ложны, и все репетиции скрываются. Требуется сопоставить точный JSON server GET `/native/projects/:projectId/rehearsals` и лишь после этого присвоить finding/критичность. Ручная проверка после разрешения запуска: одинаковая репетиция на проекте и календаре, UTC− и timezone профиля, отличная от устройства. При подтверждении date-only отдельный fix 1–2 часа; общий нормализованный контракт времени 0.5–1 день.

## Стыки и исключённые подозрения

- B ↔ A: lifetime ProjectProvider на logout подтверждён `App.tsx`; BC01.
- B ↔ D: форма использует старый selectedProject, подтверждено фрагментом; BC02. Полный аудит формы — в D.
- B ↔ D: JSON getAll против прямого date/time rendering пока требует сверки; BC04.
- B ↔ server invites: `JoinProjectScreen.tsx:118-124` трактует любой HTTP 400 как already-member. Проверяющий сервер подтвердил, что сейчас 400 есть только для already-member, остальные ошибки 404/410/500. Не включать как самостоятельную находку.
- B ↔ navigation: JoinProject берёт `route.params.code` только в initializer (`:28,32`); изменение code в уже открытом экземпляре не синхронизируется. Требуется проверить поведение повторного deep link в navigation; пока не finding.
- `useInviteLink.test.ts:165-191` заявляет concurrent calls, но обе операции await последовательно. Это пробел проверки, не самостоятельный bug. При разрешении запуска воспроизвести две overlapping operations и изменение generatingFor.
- Ошибки initial fetch в ProjectsScreen дают только error без retry (`:69-72`), но другие переходы могут перезагрузить данные; улучшение восстановления, не отдельная высокоприоритетная находка в этом проходе.
