## Замечания к контракту и коду

### R3-01 — P1, контракт A01: уже привязанный OAuth обходит очистку старого недоверенного credential

**Место:** `audit/REMEDIATION_R3.md:63–67`. Соответствующая существующая ветка: `rehearsal-calendar-native/server/utils/accountLinking.js:49–67`.

Фраза «Провайдер уже привязан — вход» оставляет без обработки legacy-аккаунты, где A01 **уже произошёл до R3**: атакующий заранее зарегистрировал адрес с собственным паролем, владелец уже вошёл через Google/Apple, и прежний код привязал OAuth, сохранив пароль атакующего. На следующем OAuth-входе эта запись попадает в первую ветку, а не в коллизию из следующего пункта. Снятие пароля и отзыв сессий не происходят.

**Воспроизведение на локальном PG:** создать password-аккаунт с адресом владельца; добавить ранее привязанную строку Google с его проверенным subject/email; строки `native_email_identities` нет. Вызвать `findOrCreateOAuthUser` с этим же подтверждённым provider/subject, затем выполнить password-login прежним паролем и GET `/auth/me` с прежним access token. В независимом прогоне: `linked=false`, оба HTTP **200**, `token_version=1`. Проверка выполнялась после границы верификации, с синтетическим subject; обращения к Google не было.

Это не претензия к отсутствующему пока endpoint A01: **сама предложенная ветвь контракта разрешает прежнее поведение**.

**Что требуется:** решение по недоверенному паролю/identity и сессиям должно применяться и при найденном provider, под тем же user lock. Проверять совпадение подтверждённого адреса с текущим адресом аккаунта; отсутствие email в повторном Apple-токене не считать новым доказательством владения адресом. Добавить сценарии pre-linked legacy, новый pending и новый verified; у атакующего после законного восстановления должны отказать пароль, access и refresh.

### R3-02 — P2, A03: Intl принимает offset-строки, которые PostgreSQL трактует иначе или отвергает

**Место:** `rehearsal-calendar-native/server/utils/accountInput.js:51–55,79–81`. SQL-потребители: `server/routes/native/availability.js:123,194`.

Успешный `new Intl.DateTimeFormat(..., { timeZone })` на закреплённом Node 22 **не означает IANA identifier**. Например, `+03:00`, `+0300`, `-0330` проходят этот guard и сохраняются через PUT `/api/auth/me` с HTTP 200.

**Воспроизведение на каноничной PG-схеме:**

1. Войти в локальный fixture-аккаунт и отправить `PUT /api/auth/me` с `{"timezone":"-0330"}` — получено 200.
2. Иметь хотя бы одну ручную availability-строку этого пользователя.
3. `DELETE /api/native/availability/2026-10-01` — получено **500**, SQLSTATE **22023** (`time zone not recognized`).

Для `+03:00` ошибки SQL нет, но данные интерпретируются по-разному. Для instant `2026-10-01T22:00:00Z` фактически получено:

| Потребитель | Местные дата и время |
|---|---|
| `timestampToLocal(..., '+03:00')` / Intl | `2026-10-02 01:00` |
| PostgreSQL `AT TIME ZONE '+03:00'` | `2026-10-01 19:00` |

То есть валидация допускает не только последующий 500, но и выбор другого дня при удалении/замене доступности.

**Что требуется:** проверять выбранный контракт именованных зон, совместимый с используемыми JS/PG-потребителями; числовые offsets не пропускать как IANA-зоны. Регресс — реальный PostgreSQL и HTTP, с положительными UTC/Asia/Jerusalem и отрицательными offset-строками. Одного SQLite/Jest недостаточно: SQLite fixture удаляет `AT TIME ZONE` из запросов.

### R3-03 — P2, A03: строки с NUL доходят до PostgreSQL вместо отказа 400

**Место:** `rehearsal-calendar-native/server/utils/accountInput.js:43–48,61–76`.

Проверки email/имени/необязательного текста учитывают тип и длину, но допускают U+0000, который PostgreSQL text/varchar не хранит. JSON с `\u0000` корректен; это не ошибка разбора HTTP body.

**Воспроизведение на локальном PG:**

- `POST /api/auth/register` с валидными email/password и `"firstName":"A\u0000B"` → **500**, `Failed to register user`.
- `PUT /api/auth/me` с `{"lastName":"A\u0000B"}` → **500**, `Failed to update user info`.

Оба ответа воспроизведены на HEAD. Драйвер получает SQLSTATE 22021. Типовой Jest на SQLite этот контракт хранения PostgreSQL не доказывает.

**Что требуется:** отклонять непредставимые текстовые значения до SQL и возвращать стабильный 400; добавить PG-проверку отсутствия записи/изменения. Это продолжение A03, не повод ослаблять ограничения БД.

## Недостающие правила будущего контракта

Эти пункты — требования к ещё не реализованным flows, **не заявления о воспроизведённой уязвимости несуществующего endpoint**.

**Коды после изменения credentials.** Места: `audit/REMEDIATION_R3.md:29–34,74–85`; `server/migrations/010-email-verification.sql:22–35`. Сейчас явно задан один живой код на `(user,purpose)`, но не задана судьба остальных кодов после reset, смены адреса или разрешения OAuth-коллизии. `token_version + 1` отзывает JWT, не строки кодов. Зафиксировать связывание challenge с актуальным адресом/состоянием credentials и атомарное потребление/инвалидацию применимых старых challenges под user lock.

Сценарий проверки: запросить reset-код на старый адрес, подтвердить смену email, затем отправить старые email+reset-code в confirm. Ожидание — отказ без изменения нового email/password/identity/token_version. Аналогично проверить старые verify/change-коды после takeover/reset и два concurrent confirm одного кода (ровно один успех). Подмена `purpose` или адреса с тем же кодом тоже должна отказывать.

**Смена email у OAuth-only пользователя.** Место: `audit/REMEDIATION_R3.md:83–85`. Запрос содержит `currentPassword`, которого у такого пользователя нет. Нужно явно выбрать рабочее доказательство текущего контроля аккаунта — например, свежий OAuth proof или подтверждение текущего доказанного адреса. Только код на **новый**, выбранный инициатором адрес этого не доказывает. Сценарий: украденный JWT OAuth-only аккаунта + ящик атакующего не должны позволять незаметно сменить адрес и получить постоянный пароль через reset. Проверить также отсутствие/недоступность старого адреса и Apple relay. Не выдавать парольный параметр за решение этого случая.

**Доставка и нейтральный reset-ответ.** Места: `audit/REMEDIATION_R3.md:27–34,72–73`. Согласовать приоритет `503 EMAIL_UNAVAILABLE` и «всегда 202», а также форму ответа: возврат `delivery` не должен различать существующий/несуществующий email в reset-request. После COMMIT возможны crash до отправки и потерянный ответ mail-provider; явно описать unknown/retry, не обещая доставку. Проверить, что resend и попытки кода ограничены атомарно, включая параллельные запросы, а отсутствие транспорта не оставляет пользовательских записей.

**Первый пароль пока противоречит целевому контракту.** Места: `server/routes/auth.js:344–352`, `server/__tests__/routes/accountInput.test.js:174–177`; требование verified — `audit/REMEDIATION_R3.md:90–92`. На HEAD OAuth-аккаунт без identity получает первый пароль с HTTP 200; независимый PG-прогон это подтвердил. Это ожидаемая незавершённость почтовой части, но текущий тест закрепляет именно отсутствие проверки. При завершении R3 нужны разные положительный verified и отрицательные legacy/pending сценарии; нынешний 200-тест нельзя сохранить как общий контракт.

Нормализация email и разрешение существующих case-коллизий перед unique lower(email), поведение pending после потерянного 201/ошибки отправки и восстановление занятого адреса тоже должны попасть в конечные сценарии. Не выдавать pending сессию ни через login, ни через refresh/старый token, ни из повторной регистрации. Решения «код вместо ссылки», «не объявлять legacy verified», «сервер перед клиентом с явным отказом старой регистрации» в целом разумны. Отзыв недоверенного пароля при доказанном OAuth-входе разумен с исправлением R3-01.

## Группа 010 и изменение v1

**Место:** `server/database/schema/README.md:93–106`; `server/database/schema/manifest.mjs:17–61`; `server/database/migrations/history.mjs:80–87`.

Перепривязка действительно меняет identity уже названных профилей, а не только добавляет независимый шаг. Независимый тест: получить 19-табличную БД через настоящий `--fresh` из `eb24c62`, оставить записанный `native_schema_history`, затем вызвать `--dry` и `--apply` из `72fc97d`. Оба возвращают **HISTORY_INVALID**, журнал не меняется. Новая версия не может обновить ранее управляемую v1-БД до 010. Отказ безопасный; данные не портятся.

**С обоснованием согласен только как с явным исключением до первого постоянного использования**, если утверждение «все прежние БД одноразовые, production/staging/local persistent нигде не adopted» действительно подтверждено. Отсутствия production adoption одного недостаточно. Из кода наличие/отсутствие чужих постоянных БД проверить нельзя; в этом ревью их инвентаризация NOT_RUN. При указанной предпосылке не считаю обязательным заводить v2 только ради одноразовых тестовых историй, но это сознательная несовместимость и корректировка обещания после R2 VERIFIED, а не доказанная совместимая миграция.

Если существует хотя бы одна сохраняемая история прежнего v1, нужны неизменные старые артефакты и именованный переход на новую версию. Перехешировать записи ledger или удалять историю для обхода отказа нельзя. До принятия первого постоянного v1 стоит закрепить именно финальный контракт R3: последующие правки 010 уже потребуют обычной версионированной миграции. Проверка «схема R2 → R3 на той же БД с сохранённым журналом» должна стать явным upgrade-gate, когда совместимость начнёт обещаться.

### R3-05 — P3: контракт неизвестного исхода отправки расходится с failed_at

**Место:** `audit/REMEDIATION_R3.md:128–129`; реализация — `rehearsal-calendar-native/server/services/email/transport.js:59–61` и `rehearsal-calendar-native/server/services/email/codes.js:131–144`; закрепляющий поведение тест — `server/__tests__/services/emailCodes.test.js:115–128`.

Контракт говорит: при сбое после COMMIT до ответа провайдера у строки нет ни `sent_at`, ни `failed_at`. При таймауте ответа нет, однако транспорт возвращает `{ok:false, reason:'TIMEOUT'}`, а deliverCode без различения причины записывает `failed_at` и возвращает `failed`. Сетевой обрыв проходит тем же путём. Комментарий «record what the provider said» также не описывает этот случай: ответа провайдера не было. Причина TIMEOUT/NETWORK в строке не сохраняется, поэтому по одному `failed_at` нельзя отличить такой исход от явного HTTP-отказа.

**Воспроизведение без внешней сети:** передать emailTransport инъекцию request, которая фиксирует принятие запроса заглушкой, не возвращает ответ и отклоняет promise по штатному `signal.abort`; затем вызвать настоящий deliverCode с записывающей SQL заглушкой db. Через **8008 мс** получены `TimeoutError`, результат `failed` и запрос `UPDATE native_email_codes SET failed_at = NOW() WHERE id = $1`, хотя ответ не получен. Скрипт — `/private/tmp/reh-review3-extra.mjs`, вывод — `/private/tmp/reh-review3-extra.log`. Сохранение failed_at в настоящей SQLite-фикстуре отдельно подтверждено существующим тестом `records a failed delivery on the code row`, который проходит в общем Jest. Заглушка принятия моделирует неопределённый исход; фактическую отправку Resend этот опыт не измеряет.

**Оценка и требуемое уточнение:** считать таймаут неудачной *попыткой* допустимо и не создаёт показанного обхода проверки кода. Рекомендую закрепить именно это значение `failed_at`/`failed` и явно ограничить правило о двух NULL аварийным завершением до записи результата. В контракте и дальнейшем клиентском тексте нельзя превращать такое состояние в утверждение «провайдер точно не принял/не отправил письмо». Если требуется различать отказ и неизвестный исход средствами БД/API, нужен отдельный результат unknown; тогда меняются реализация и тест. Достаточно выбрать одну согласованную семантику до подключения маршрутов. Сейчас это низкоприоритетное замечание к модели состояния и документации, а не доказанный дефект доставляемости или захват аккаунта.

### R3-06 — P2: verify-email выдаёт новую версию сессии по доказательству прежнего пароля

**Место:** `rehearsal-calendar-native/server/routes/emailVerification.js:59–66`; транзакция подтверждения завершается на строке 56. Существующая смена пароля и отзыв: `server/routes/auth.js:378–383`.

Пароль корректно перепроверяется под user row lock. Но после COMMIT маршрут заново читает пользователя, включая **текущий token_version**, и подписывает токены этой версией. Если между COMMIT и чтением другой запрос сменил пароль и увеличил версию, подтверждение, выполненное со старым паролем, получает уже новую версию. Такие токены переживают отзыв, ради которого версия увеличивалась.

**Воспроизведение на настоящем PG и HTTP, без OAuth и будущего reset-потока:**

1. Создать legacy-аккаунт с паролем, без identity; войти через `/api/auth/login`, получить обычную сессию версии 1. Через `/api/auth/verify-email/resend` получить код в capture-for-tests.
2. Начать `/api/auth/verify-email` со старым паролем и кодом. Удержать выполнение **после COMMIT**, перед финальным SELECT на строках 59–65. В независимом сценарии пауза ставится обёрткой db.get только для этого запроса; SQL, транзакции и маршруты приложения остаются настоящими.
3. Убедиться другим соединением, что identity уже verified, а token_version ещё 1. На исходной сессии выполнить настоящий `PUT /api/auth/me` с currentPassword и новым password: **200**, версия становится 2. Исходный access token теперь получает **401**.
4. Освободить подтверждение. Получено **200**, оба токена подписаны версией 2: access допускается на `/api/auth/me` (**200**), refresh тоже получает **200**. При этом обычный login со старым паролем получает **401**.

Таким образом, отзыв сессий после смены пароля работает для старого токена, но пропускает токен, созданный новым маршрутом из старого доказательства. Нужны одновременные запросы и код/пароль, действительные до смены; это не обход без credentials. Уже существующий PG-тест меняет пароль **до получения блокировки** и эту другую границу не покрывает.

**Что исправлять:** привязать выдаваемую пару к версии credentials, прочитанной вместе с проверкой под той же блокировкой. Например, вернуть из транзакции данные пользователя и token_version, которыми разрешена выдача, и после успешного COMMIT подписывать именно эту версию. Последующий отзыв тогда делает запоздало возвращённые токены непригодными. Другой допустимый вариант — повторная проверка с отказом при изменении версии; нельзя просто брать новую версию из отдельного SELECT. Регресс: управляемый барьер после COMMIT, параллельные password-change/logout, затем отказ access и refresh, основанных на старой версии; прежний тест изменения пароля до lock тоже сохранить.

Аккаунт при этом уже verified, поэтому следующий вход владельца через Google только входит, а пароль чужака остаётся. Захват, случившийся до R3, переживает исправление и становится ещё незаметнее.

**Воспроизведение на настоящем PostgreSQL 15.13** (R0-harness, loopback, внешних соединений 0). Использована временная копия сервера без `.env`, где заменён только вход сценария R3_AUTH на `probe/r3Auth.review.mjs`. Маршруты, adapter, SQL и `signInWithProvider` — из b8a86fc.

1. Legacy-аккаунт владельца с паролем чужака и без identity. Вариант «а» — с заранее привязанным Google владельца (форма R3-01), вариант «б» — без привязки (первый вход через Google). Чужак входит по паролю: 200, версия 1.
2. Управляющее соединение держит `FOR UPDATE` строки пользователя. Первым в очередь встаёт `signInWithProvider` владельца, вторым — `PUT /api/auth/me {"password": "<новый>"}` с access-токеном чужака, **без `currentPassword`**. Перед освобождением оба наблюдаются ожидающими блокировку (`waiting = 2`).
3. После освобождения вход владельца даёт `passwordRevoked: true` и подписанную версию 2. `PUT /me` чужака отвечает **200 с access и refresh**. В строке: пароль есть, `token_version = 3`, identity `verified/google`, способы входа `email, google`.
4. Сессия владельца (версия 2) на `GET /me` получает **401**. Новый access чужака — **200**, его refresh — **200**, вход чужака с новым паролем — **200**.
5. Повторный вход владельца через Google даёт `passwordRevoked: false`. Пароль чужака остаётся, вход по нему снова **200**.

Оба варианта дали одинаковый результат. Контроль на таком же fixture без гонки — `PUT /me` после COMMIT входа — отвечает **401 Session revoked**: пароля нет, сессия владельца отвечает 200. Значит, дефект именно в порядке событий. Команда — `node scripts/r0-postgres.mjs --r3-auth-only` из копии, exit 0. Это означает лишь завершение наблюдений; результат сценария назван **OBSERVED**.

Барьер управляющего соединения только фиксирует порядок. В production то же окно — время транзакции входа (около десяти запросов к Neon) плюс путь `PUT /me` от middleware до `FOR UPDATE`. Лимит `/api/auth` (20 запросов в минуту на IP) снижает шансы, но окно не закрывает. Чужаку достаточно раз в несколько секунд слать `PUT /me` без `currentPassword`: пока пароль есть, ответ 403, и сессия остаётся целой. Нужен существующий захват до R3 с живой сессией. По OPS-R3-DATA формы «а» в данных нет (пароля вместе с Google/Apple нет ни у кого). Форма «б» применима к любому из 10 аккаунтов с паролем, если этот пароль чужой.

**Что исправлять:** проверять сессию под той же блокировкой, под которой меняются credentials. Middleware передаёт версию токена (`decoded.tv`). `PUT /me` читает `token_version` вместе с `FOR UPDATE` и при `token_version > tv` отвечает 401, ничего не записывая. Привязывать это к состоянию identity нельзя: после отзыва адрес уже verified провайдером, поэтому планируемое правило «первый пароль — только при verified» (`REMEDIATION_R3.md:176–179`) этот путь не закрывает.

Та же причина — проверка версии вне блокировки — касается и других изменяющих маршрутов: logout, DELETE /me, отвязки. Наблюдался только `PUT /me`, единственный маршрут, который так возвращает доступ.

Регресс на PG — ровно этот порядок. Ожидается отказ `PUT /me`, пароля нет, версия 2, сессия владельца отвечает 200, вход чужака — 401. Последовательный случай и обратный порядок сохранить (`PUT` до входа, затем отзыв нового пароля). Мутация «без сверки версии под блокировкой» должна этот регресс ронять.

### R3-12 — P2: отзыв не снимает push-устройство чужака

**Место:** правило — `server/utils/accountLinking.js:148–159`: пароль, email-строка, `token_version`, коды; устройства не затрагиваются. Регистрация — `server/routes/native/pushTokens.js:19–80`, проверка только в middleware. Выбор получателей — `server/services/notifications/pushNotificationService.js:20–37`: по `user_id` и `notifications_enabled`, без учёта версии сессии. Контракт — `audit/REMEDIATION_R3.md:126–133,140,152–157`; API — «a request admitted just before a revocation changes nothing after it» (`docs/api-documentation.md:49–52`).

Приложение регистрирует push-токен при каждом запуске, если уведомления разрешены (`src/shared/services/notifications.ts:110–132`). Значит, у чужака, пользовавшегося захваченным аккаунтом на телефоне, есть строка в `native_push_tokens`. Правило R3-01 отзывает пароль, сессии и коды, но не устройство. Телефон чужака и дальше получает уведомления аккаунта: названия проектов и репетиций, имена участников, напоминания (`server/i18n/pushNotifications.js`). Сам владелец удалить это устройство не может: `GET /push-tokens` не отдаёт значение токена, а `DELETE` его требует. Строка исчезнет, только если на этом телефоне войдут в другой аккаунт или Expo сообщит DeviceNotRegistered.

Отдельно: регистрация, допущенная до отзыва, выполняется после него. В перечень маршрутов R3-09 она не попала.

**Воспроизведение на PostgreSQL 15.13.** Проба `probe/r3Auth.recheck.mjs` в копии сервера 8680cae; заменён только вход сценария R3_AUTH. Команда `node scripts/r0-postgres.mjs --r3-auth-only`: exit 0, OBSERVED, externalConnections 0.

- **(а)** Legacy-аккаунт с паролем чужака и привязанным Google владельца. Чужак входит и регистрирует `ExponentPushToken[review-stranger-phone-a]` → 200. Вход владельца: `passwordRevoked: true`, версия 2. Сессия чужака теперь 401, но строка устройства осталась, и `getUserPushTokens([id])` возвращает её — следующее уведомление аккаунта уйдёт на телефон чужака.
- **(б)** Регистрация чужака поставлена в очередь за входом владельца (строка удерживается, оба ожидания видны). Ответ **200** после отзыва, версия 2, строка устройства создана, `getUserPushTokens` её возвращает.

Отправка в Expo не вызывалась (harness запрещает внешние соединения). Проверен выбор получателей, которым пользуется `sendPushNotification`.

**Что исправлять:**

- В ветке отзыва удалять устройства аккаунта той же транзакцией (`DELETE FROM native_push_tokens WHERE user_id = $1`). Устройство владельца зарегистрируется снова при следующем запуске приложения.
- Регистрацию делать под `lockSession` или условным `INSERT … SELECT … WHERE token_version <= $tv`, чтобы запрос из отозванной сессии ничего не добавлял.
- Регресс на PG — ровно (а) и (б).

Та же дыра есть у logout «выйти везде»; она была известна (комментарий в `pushTokens.js:37–49`). Но для R3-01 она означает, что вытесненный захватчик продолжает читать данные владельца и его коллег.

### R3-13 — P3: OPS-R3-APPLE не даёт заявленной верхней границы

**Место:** `audit/REMEDIATION_R3.md:258–268` (решение 5) и `282–291` (карточка).

`apple_without_password` отбрасывает аккаунты, созданные входом Apple и позже получившие пароль. До R3 `PUT /me` ставил пароль без всякого доказательства (0f655e2), и production до выкладки работает на этом коде. У такого аккаунта правило R3-01 снимет пароль, но Apple-связь останется — это ровно случай R3-10. Кроме того, `count(*)` считает строки Apple-связей, а не аккаунты.

**Воспроизведение** — та же проба, SQL карточки дословно (`probe/OPS_R3_APPLE.sql`):

- A1: Apple-связь без пароля. A2: Apple-связь, затем пароль, поставленный так, как это позволял код до R3.
- Карточка: `apple_links = 2`, `apple_without_password = 1`. Apple-аккаунтов без identity при этом **2**.
- У A2 доказательство владельца через Google даёт `passwordRevoked: true`, после чего вход Apple чужака (`emailVerified: false`) **входит в тот же аккаунт**.

OPS-R3-DATA на 25.09 (`password_with_oauth = 0`) означает, что тогда таких аккаунтов не было. Но карточку выполнят позже, а старый код до выкладки может их создать.

**Что исправлять:** верхней границей считать `count(DISTINCT p.user_id)` по всем Apple-связям, без фильтра по паролю (фильтр оставить отдельной колонкой). Выполнять после выкладки R3, когда набор перестаёт расти, или повторить после неё. Фразу «множество не растёт» привязать к выкладке.

### R3-14 — P3: `lockSession` в начале DELETE /me даёт deadlock с пересборкой слотов

**Место:** `server/routes/auth.js:418` — строка пользователя берётся `FOR UPDATE` (`jwtMiddleware.js:119`) до каскада. Встречная форма — `server/services/rehearsals/slotService.js:72–75`: `updateRehearsalSlots` в одной транзакции удаляет занятые строки репетиции, затем вставляет по строке на участника. Каждая вставка берёт FK `FOR KEY SHARE` на `native_users`, а он конфликтует с `FOR UPDATE`.

Допустим, владелец проекта удаляет аккаунт, пока другой администратор меняет время репетиции, где владелец участвует. DELETE /me держит строку владельца и ждёт строки доступности, удалённые чужой транзакцией. Пересборка ждёт строку владельца. До исправления DELETE /me брал пользователя последним, и такого цикла не было.

**Воспроизведение** (та же проба). Отдельное соединение повторяет порядок SQL из `slotService.js`: DELETE строк репетиции, затем INSERT для владельца. DELETE /me идёт по HTTP.

- На 8680cae: **deadlock detected** (40P01, «while deleting tuple … in relation native_user_availability», `auth.js:473`). DELETE /me → **500** «Failed to delete account», аккаунт остаётся, `pg_stat_database.deadlocks` +1; вставка пересборки проходит.
- Та же проба в копии, где только `routes/auth.js` взят из b8a86fc (`probe-deadlock-b8a86fc-auth.log`): deadlock **0**, DELETE /me **200**, `deletedProjects: 1`.

Данные не портятся: обе транзакции целые, повтор проходит. Для сбоя нужна редкая встреча двух операций.

**Что исправлять:** один из двух вариантов; любой проверить этой же пробой и PG-контрактом R3-09 для DELETE /me.

- В `lockSession` брать `FOR NO KEY UPDATE`. Эта блокировка конфликтует со всеми писателями отзыва (`FOR UPDATE` входа, отвязки и `PUT /me`, UPDATE версии), но не с FK `FOR KEY SHARE`.
- Либо в DELETE /me сверять сессию перед удалением строки пользователя и откатывать транзакцию исключением.

### Дополнительный случай — P2: отсутствие пароля не доказывает отсутствие прежних парольных сессий

Место на b8a86fc: `rehearsal-calendar-native/server/utils/accountLinking.js:149–155`. Увеличение `token_version` и погашение кодов находятся внутри `if (user.password_hash)`. Публичная отвязка email (`accountLinking.js:258–284`) уже умеет обнулять пароль без отзыва выпущенных сессий. Поэтому пароль NULL не означает, что все действующие сессии были выданы владельцу через OAuth.

Воспроизведение на настоящем PostgreSQL 15.13, без изменения кода приложения:

1. Legacy-аккаунт без identity, пароль чужака, email-метод и ранее привязанный Google владельца. Вход чужака через HTTP даёт access/refresh версии 1; resend создаёт живой verify-код.
2. Чужак вызывает `DELETE /api/auth/me/providers/email`: 200. Пароль NULL, версия 1, код жив.
3. Владелец входит через `signInWithProvider` с подтверждённым Google текущим адресом. Identity становится verified, но версия остаётся 1, код остаётся живым, `passwordRevoked: false`.
4. Прежний access чужака на `GET /me` — **200**, прежний refresh — **200**. Гонка не нужна.

Это соответствует узкой условности контракта «legacy без пароля — привязка и identity verified», но нарушает общую гарантию отказа access/refresh чужака после восстановления (`REMEDIATION_R3.md:124–125`) и погашения кодов при коллизии OAuth (165–168). Отзыв при доказательстве ранее неподтверждённого адреса следует отделить от наличия пароля; `passwordRevoked` может отдельно сообщать о фактическом удалении пароля. В новом поручении владельца этот случай уже включён в проверку 43cbdac, поэтому отдельный новый номер R3 ему не присваивается.

### R3-17 — P3: обоснование нейтральности обещает больше, чем одинаковые status/body

**Место:** `audit/REMEDIATION_R3.md:207–211`; фактическое ожидание — `rehearsal-calendar-native/server/routes/passwordReset.js:54–56`, ранний ответ для истёкшего кода — `server/services/email/codes.js:93–97`.

Принятое решение не скрывать наличие аккаунта полностью обосновано существующим ответом регистрации 409. Однако фразы «запрос не выдаёт его сам по себе» и «только ценой письма … и попыток из пяти» неточны:

1. Request ждёт результата отправки только при найденном аккаунте. В локальной пробе транспорт остановлен на управляемой заглушке fetch; запрос отсутствующего адреса уже вернул 202, пока запрос известного адреса ещё ждал заглушку. После её освобождения оба вернули одинаковые status/body. Это подтверждает различие пути ожидания, не измеряет задержку настоящего Resend и не доказывает статистическую надёжность удалённого определения адреса.
2. Для ранее выпущенного, но истёкшего reset-кода confirm возвращает **CODE_EXPIRED**, для отсутствующего адреса — **CODE_MISSING**. Два запроса к истёкшему коду оставили `attempts = 0`: пяти попыток такой ответ не расходует. В пробе провайдер перед этим ответил HTTP 422, `failed_at` заполнен, `sent_at` пуст: принятого письма тоже нет. Наличие отказа транспорта не удаляет строку кода, как и предусмотрено общим сервисом.

**Нужно:** описать гарантию точно: одинаковые status/body request, без delivery и без раскрытия адресного лимита; равенство времени ответа не гарантируется, confirm может различать отсутствие и истечение кода без расхода попыток. Не обещать обязательное письмо владельцу. При текущем осознанном контракте это поправка текста, а не требование нового механизма сокрытия адресов.

Вместе с HP01 оно превращает пароль из доказательства держателя в то, что сессия выдаёт себе сама.

**Воспроизведение.** Настоящие роутеры `auth`, `emailVerification`, `passwordReset` и `emailChange` на SQLite-харнессе, в копии `git archive 239b5d7` вне репозитория. Проверка Google заменена её claims, как в `providerSignIn.test.js`; почта — `capture-for-tests`. Строки `PROBE` — в `probe-jest.log`, команда — в таблице прогонов.

1. **Контроль.** Аккаунт создан входом `POST /auth/google`; у вора только его access. `change` без пароля → 202, `currentCodeRequired: true`. `confirm` одним кодом из ящика вора → **400** `CODE_INVALID`, `field: currentCode`, адрес прежний. Пока пароля нет, защита работает.
2. **Обход.** Тот же аккаунт. `PUT /me { password }` этой сессией → **200** и новая пара. `change { newEmail: адрес вора, currentPassword: только что заданный }` → **202**, `currentCodeRequired: false`, `delivery: { newAddress: "sent" }`. `confirm` кодом из ящика вора → **200**: адрес аккаунта теперь адрес вора. До переноса на адрес владельца не ушло ни одного кода (0); уведомление приходит уже после. Дальше отвязка Google той же сессией → 200. Сброс пароля на адрес владельца → 202 и 0 писем: аккаунта с этим адресом больше нет. Вход владельца тем же Google создаёт **новый** аккаунт (`isNewUser: true`, другой id). Вход вора паролем → 200. Самостоятельного пути назад у владельца нет, остаётся support из уведомления.
3. **Вариант с паролем.** Владелец зарегистрировался с паролем, подтвердил адрес кодом и привязал Google. Вор с его сессией: `change` без пароля → 403 `CURRENT_PASSWORD_INVALID`. `DELETE /me/providers/email` → **200**: пароль снят, сессия цела. `PUT /me { password }` → **200**; `change` → 202, `currentCodeRequired: false`; `confirm` → **200**, адрес вора. Вход владельца прежними адресом и паролем → 401.
4. **Граница.** Legacy-аккаунт Google без identity на первый пароль получает 403 `EMAIL_NOT_VERIFIED`, но после одного входа через Google — 200, тот же аккаунт. Значит, после выкладки уязвим каждый аккаунт без пароля (с первого входа через провайдера) и каждый аккаунт с паролем и связью Google/Apple. Защищён только аккаунт с одним паролем без связей.

Access-токен по умолчанию живёт 30 дней (`config/tokenTtl.js:20`), так что украденная сессия — не мгновение. До HP01 такой вор тоже мог поставить пароль, но владелец возвращал аккаунт сбросом через свой ящик. С HP01 вор уносит и ящик.

**Что исправлять:** доказательство держателя для смены должно быть тем, чего сессия сама себе не выдаёт. Выбор за владельцем:

- (а) закрыть оба пути, где одна сессия создаёт или снимает пароль: первый пароль — только с кодом на текущий адрес или свежим входом через провайдера, отвязка пароля — с `currentPassword`. Тогда пароль снова доказывает держателя, обе ветки смены остаются как есть, и заодно закрывается прежний путь, где сессия ставила пароль, переживающий все сессии;
- (б) требовать код на текущий адрес (или свежий вход через провайдера) при каждой смене у аккаунта без пароля или со связью Google/Apple.

Регрессы на обе формы: Google-only verified — сессия ставит первый пароль и меняет адрес; пароль + Google — сессия отвязывает пароль, ставит новый и меняет адрес. В обоих перенос без кода на текущий адрес невозможен, адрес прежний. Мутация, возвращающая нынешнее поведение, должна их ронять. Контракт, API и CLAUDE.md привести к выбранному правилу.

### R3-20 — P3: без пароля неверный код нового адреса сжигает код текущего

**Место:** `server/routes/emailChange.js:97–104`. Код текущего адреса проверяется первым и при успехе сразу гасится (`server/services/email/codes.js:114`). Затем неверный код нового адреса возвращает 400, и транзакция коммитит оба изменения. Контракт (`REMEDIATION_R3.md:244–245`) и API (`api-documentation.md:514–515`) описывают только обратный случай: неверный текущий не тратит код нового адреса.

**Воспроизведение** (та же проба, `PROBE burn`). Аккаунт без пароля, `change` → 202. `confirm { code: неверный, currentCode: верный }` → 400 `CODE_INVALID`, `field: code`. В таблице код `confirm` погашен (attempts 0), `change` жив с attempts 1. Затем `confirm` с **верной** парой → **400** `CODE_MISSING`, `field: currentCode`, адрес прежний. Новый запрос сразу → 429 `RATE_LIMITED`, `retryAfter: 60`.

Безопасности это не вредит: поток только строже. Но у аккаунта без пароля пять попыток кода нового адреса на деле сводятся к одной на запрос. Каждая опечатка — новая пара писем и минута ожидания, пять за час — блокировка до часа.

**Что исправлять:** гасить код текущего адреса только вместе с успешным кодом нового: проверить оба, засчитать попытку неверному, погасить оба только при двух успехах. Route-тест: верный текущий и неверный новый, затем верная пара → 200. В контракте и API — что тратится при каждой ошибке.

| 2. Транзакции и порядок блокировок | **Принято.** Обе ручки сначала берут строку пользователя (`FOR NO KEY UPDATE`), потом коды. С неё же начинают reset (`FOR UPDATE` по email), verify-email/resend, Google/Apple, `PUT /me`, `DELETE /me`, отвязка и push-токен; register пишет только новые строки. Нюанс: `UPDATE … SET email` меняет ключ (email UNIQUE) и поднимает блокировку до `FOR UPDATE`, то есть ждёт держателей FK `FOR KEY SHARE`. `PROBE keyshare`: подтверждение ждало (`transactionid`, UPDATE email) транзакцию, которая лишь вставила этому пользователю уведомление, и прошло после её COMMIT (200); та же блокировка не задержала `PUT /me` с именем (0 ожидающих, 200). Верный текущий и неверный новый — код текущего сгорает (R3-20): для безопасности приемлемо, как UX — нет, и описание говорит иное. | 4. Отзыв и устройства | **Принято.** `token_version + 1` в той же транзакции; пара подписана версией, прочитанной через `SESSION_USER_COLUMNS` до COMMIT; прежний access — 401 (route-тест и PG). Удаление в storage остаётся доступным — ошибка касается одной операции, а не полного отказа хранилища. Реальная `syncUserPreferences` (`src/shared/utils/storage.ts:16–29`) не перехватывает отказ `AsyncStorage.multiSet`, поэтому этот исход соответствует её контракту.

Тест `REVIEW R3-30: a rejected write after cancellation must remove the abandoned tokens` ожидает отсутствие трёх ключей. Фактически React user — `null`, но access=`cancelled-access`, refresh=`cancelled-refresh`, cachedUser содержит A. Проба падает на своём утверждении, без ошибок загрузки. По коду `loadUser` (`:185–225`) эти сохранённые credentials позволяют следующему запуску восстановить оставленную сессию; сам перезапуск устройства этой пробой не выполнялся.

**Что требуется:** предусмотреть согласованный откат частично записанной сессии и при исключении, сохранив исключительное владение очередью. Тест должен отказывать после первой записи, когда очистка ещё возможна, и проверять отсутствие credentials оставленной попытки. `sessionWrites.current = run.catch(...)` обеспечивает продолжение очереди, но данные не откатывает.

### R3-31 — P2: отмена после начала очистки стирает календарное состояние возвращающегося пользователя

**Место:** `src/contexts/AuthContext.tsx:95–116`, особенно `:100–109`; вызывающая сторона — `:168–169`. Комментарий `:92–94` обещает сохранность устройства после оставленной попытки.

Между `left()` на `:98` и вызовом `multiRemove` на `:100` нет await: другой JS-обработчик не вклинится между этими синхронными строками. Оставшееся окно — **после запуска асинхронного удаления и до его завершения**. Отмена в этот момент не отменяет уже начатую операцию; после её завершения старая попытка ещё сбрасывает connection cache и записывает owner A. Вызывающая сторона затем откатывает только токены/cachedUser. Очередь сохраняет данные, которые B запишет позже, но не восстанавливает данные B, существовавшие до попытки A.

**Воспроизведение:** в storage owner=`8`, mappings=`mappings-of-B`, availability-cache=`cache-of-B`. Подтверждение A (id 7) доходит до `multiRemove`; удержать завершение удаления. Отменить A, начать вход B (id 8): B правильно ждёт очередь. Разрешить удаление, дождаться A и B. Получены правильные user=8, access=`new-access`, owner=`8`, но mappings и cache — **undefined**. A так и не завершила вход, а B вернулся к своему аккаунту с потерянными календарными данными.

Тест `REVIEW R3-31: cancelling after deletion starts must preserve the returning users calendar state` падает именно на двух удалённых значениях. API и native IO подменены; promise задаёт допустимый порядок завершения асинхронной операции, а не имитирует её физическую отмену. Прежняя проба с остановкой на чтении owner теперь зелёная — это другой момент отмены.

**Что требуется:** определить и обеспечить согласованную границу фиксации локального входа и отмены относительно разрушительной очистки. Либо оставленная попытка сохраняет/восстанавливает прежнее состояние, либо UI и контракт явно исключают отмену после согласованной точки фиксации. Ещё одна проверка после удаления не восстановит mappings. Это остаток заявленного исправления R3-29, а не доказательство повторного удаления токенов уже завершившегося входа B.

### Очередь, ожидание и другие записи в storage

**Исключения очередь не отравляют.** Дополнительный контроль удерживает A на настройках, ставит B в очередь, отменяет A и отклоняет её операцию. B после этого успешно входит, получает свои токены, `busy === false`. Циклического ожидания внутри `startSession` не обнаружено; сетевой запрос завершается до постановки записи в очередь.

**Ожидание local IO не ограничено временем.** Если promise AsyncStorage/настроек никогда не завершится, все последующие записи этой очереди будут ждать его без срока. Смена номера попытки не завершает уже запущенный native promise. Пробы подтверждают ожидание B до освобождения барьера; постоянное зависание native storage на устройстве не проверялось. Это ограничение решения, а не найденная внутренняя взаимоблокировка. Просто выпускать B по таймауту при продолжающейся записи A небезопасно — это вернёт исходную гонку.

Проверены и записи вне `sessionWrites`. Они не менялись в рассматриваемом диапазоне; наличие очереди у четырёх входов не означает общей защиты всех сессионных операций:
