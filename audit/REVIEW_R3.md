## Замечания к контракту и коду

### R3-01 — P1, контракт A01: уже привязанный OAuth обходит очистку старого недоверенного credential

**Место:** `audit/REMEDIATION_R3.md:63–67`. Соответствующая существующая ветка: `rehearsal-calendar-native/server/utils/accountLinking.js:49–67`.

Фраза «Провайдер уже привязан — вход» оставляет без обработки legacy-аккаунты, где A01 **уже произошёл до R3**: атакующий заранее зарегистрировал адрес с собственным паролем, владелец уже вошёл через Google/Apple, и прежний код привязал OAuth, сохранив пароль атакующего. На следующем OAuth-входе эта запись попадает в первую ветку, а не в коллизию из следующего пункта. Снятие пароля и отзыв сессий не происходят.

**Воспроизведение на локальном PG:** создать password-аккаунт с адресом владельца; добавить ранее привязанную строку Google с его проверенным subject/email; строки `native_email_identities` нет. Вызвать `findOrCreateOAuthUser` с этим же подтверждённым provider/subject, затем выполнить password-login прежним паролем и GET `/auth/me` с прежним access token. В независимом прогоне: `linked=false`, оба HTTP **200**, `token_version=1`. Проверка выполнялась после границы верификации, с синтетическим subject; обращения к Google не было.

Это не претензия к отсутствующему пока endpoint A01: **сама предложенная ветвь контракта разрешает прежнее поведение**.

**Что требуется:** решение по недоверенному паролю/identity и сессиям должно применяться и при найденном provider, под тем же user lock. Проверять совпадение подтверждённого адреса с текущим адресом аккаунта; отсутствие email в повторном Apple-токене не считать новым доказательством владения адресом. Добавить сценарии pre-linked legacy, новый pending и новый verified; у атакующего после законного восстановления должны отказать пароль, access и refresh.

### R3-02 — P2, A03: Intl принимает offset-строки, которые PostgreSQL трактует иначе или отвергает

**Место:** `rehearsal-calendar-native/server/utils/accountInput.js:51–55,79–81`. SQL-потребители: `server/routes/native/availability.js:123,194`.

Успешный `new Intl.DateTimeFormat(..., { timeZone })` на закреплённом Node 22 **не означает IANA identifier**. Например, `+03:00`, `+0300`, `-0330` проходят этот guard и сохраняются через PUT `/api/auth/me` с HTTP 200.

**Воспроизведение на каноничной PG-схеме:**

1. Войти в локальный fixture-аккаунт и отправить `PUT /api/auth/me` с `{"timezone":"-0330"}` — получено 200.
2. Иметь хотя бы одну ручную availability-строку этого пользователя.
3. `DELETE /api/native/availability/2026-10-01` — получено **500**, SQLSTATE **22023** (`time zone not recognized`).

Для `+03:00` ошибки SQL нет, но данные интерпретируются по-разному. Для instant `2026-10-01T22:00:00Z` фактически получено:

| Потребитель | Местные дата и время |
|---|---|
| `timestampToLocal(..., '+03:00')` / Intl | `2026-10-02 01:00` |
| PostgreSQL `AT TIME ZONE '+03:00'` | `2026-10-01 19:00` |

То есть валидация допускает не только последующий 500, но и выбор другого дня при удалении/замене доступности.

**Что требуется:** проверять выбранный контракт именованных зон, совместимый с используемыми JS/PG-потребителями; числовые offsets не пропускать как IANA-зоны. Регресс — реальный PostgreSQL и HTTP, с положительными UTC/Asia/Jerusalem и отрицательными offset-строками. Одного SQLite/Jest недостаточно: SQLite fixture удаляет `AT TIME ZONE` из запросов.

### R3-03 — P2, A03: строки с NUL доходят до PostgreSQL вместо отказа 400

**Место:** `rehearsal-calendar-native/server/utils/accountInput.js:43–48,61–76`.

Проверки email/имени/необязательного текста учитывают тип и длину, но допускают U+0000, который PostgreSQL text/varchar не хранит. JSON с `\u0000` корректен; это не ошибка разбора HTTP body.

**Воспроизведение на локальном PG:**

- `POST /api/auth/register` с валидными email/password и `"firstName":"A\u0000B"` → **500**, `Failed to register user`.
- `PUT /api/auth/me` с `{"lastName":"A\u0000B"}` → **500**, `Failed to update user info`.

Оба ответа воспроизведены на HEAD. Драйвер получает SQLSTATE 22021. Типовой Jest на SQLite этот контракт хранения PostgreSQL не доказывает.

**Что требуется:** отклонять непредставимые текстовые значения до SQL и возвращать стабильный 400; добавить PG-проверку отсутствия записи/изменения. Это продолжение A03, не повод ослаблять ограничения БД.

## Недостающие правила будущего контракта

Эти пункты — требования к ещё не реализованным flows, **не заявления о воспроизведённой уязвимости несуществующего endpoint**.

**Коды после изменения credentials.** Места: `audit/REMEDIATION_R3.md:29–34,74–85`; `server/migrations/010-email-verification.sql:22–35`. Сейчас явно задан один живой код на `(user,purpose)`, но не задана судьба остальных кодов после reset, смены адреса или разрешения OAuth-коллизии. `token_version + 1` отзывает JWT, не строки кодов. Зафиксировать связывание challenge с актуальным адресом/состоянием credentials и атомарное потребление/инвалидацию применимых старых challenges под user lock.

Сценарий проверки: запросить reset-код на старый адрес, подтвердить смену email, затем отправить старые email+reset-code в confirm. Ожидание — отказ без изменения нового email/password/identity/token_version. Аналогично проверить старые verify/change-коды после takeover/reset и два concurrent confirm одного кода (ровно один успех). Подмена `purpose` или адреса с тем же кодом тоже должна отказывать.

**Смена email у OAuth-only пользователя.** Место: `audit/REMEDIATION_R3.md:83–85`. Запрос содержит `currentPassword`, которого у такого пользователя нет. Нужно явно выбрать рабочее доказательство текущего контроля аккаунта — например, свежий OAuth proof или подтверждение текущего доказанного адреса. Только код на **новый**, выбранный инициатором адрес этого не доказывает. Сценарий: украденный JWT OAuth-only аккаунта + ящик атакующего не должны позволять незаметно сменить адрес и получить постоянный пароль через reset. Проверить также отсутствие/недоступность старого адреса и Apple relay. Не выдавать парольный параметр за решение этого случая.

**Доставка и нейтральный reset-ответ.** Места: `audit/REMEDIATION_R3.md:27–34,72–73`. Согласовать приоритет `503 EMAIL_UNAVAILABLE` и «всегда 202», а также форму ответа: возврат `delivery` не должен различать существующий/несуществующий email в reset-request. После COMMIT возможны crash до отправки и потерянный ответ mail-provider; явно описать unknown/retry, не обещая доставку. Проверить, что resend и попытки кода ограничены атомарно, включая параллельные запросы, а отсутствие транспорта не оставляет пользовательских записей.

**Первый пароль пока противоречит целевому контракту.** Места: `server/routes/auth.js:344–352`, `server/__tests__/routes/accountInput.test.js:174–177`; требование verified — `audit/REMEDIATION_R3.md:90–92`. На HEAD OAuth-аккаунт без identity получает первый пароль с HTTP 200; независимый PG-прогон это подтвердил. Это ожидаемая незавершённость почтовой части, но текущий тест закрепляет именно отсутствие проверки. При завершении R3 нужны разные положительный verified и отрицательные legacy/pending сценарии; нынешний 200-тест нельзя сохранить как общий контракт.

Нормализация email и разрешение существующих case-коллизий перед unique lower(email), поведение pending после потерянного 201/ошибки отправки и восстановление занятого адреса тоже должны попасть в конечные сценарии. Не выдавать pending сессию ни через login, ни через refresh/старый token, ни из повторной регистрации. Решения «код вместо ссылки», «не объявлять legacy verified», «сервер перед клиентом с явным отказом старой регистрации» в целом разумны. Отзыв недоверенного пароля при доказанном OAuth-входе разумен с исправлением R3-01.

## Группа 010 и изменение v1

**Место:** `server/database/schema/README.md:93–106`; `server/database/schema/manifest.mjs:17–61`; `server/database/migrations/history.mjs:80–87`.

Перепривязка действительно меняет identity уже названных профилей, а не только добавляет независимый шаг. Независимый тест: получить 19-табличную БД через настоящий `--fresh` из `eb24c62`, оставить записанный `native_schema_history`, затем вызвать `--dry` и `--apply` из `72fc97d`. Оба возвращают **HISTORY_INVALID**, журнал не меняется. Новая версия не может обновить ранее управляемую v1-БД до 010. Отказ безопасный; данные не портятся.

**С обоснованием согласен только как с явным исключением до первого постоянного использования**, если утверждение «все прежние БД одноразовые, production/staging/local persistent нигде не adopted» действительно подтверждено. Отсутствия production adoption одного недостаточно. Из кода наличие/отсутствие чужих постоянных БД проверить нельзя; в этом ревью их инвентаризация NOT_RUN. При указанной предпосылке не считаю обязательным заводить v2 только ради одноразовых тестовых историй, но это сознательная несовместимость и корректировка обещания после R2 VERIFIED, а не доказанная совместимая миграция.

Если существует хотя бы одна сохраняемая история прежнего v1, нужны неизменные старые артефакты и именованный переход на новую версию. Перехешировать записи ledger или удалять историю для обхода отказа нельзя. До принятия первого постоянного v1 стоит закрепить именно финальный контракт R3: последующие правки 010 уже потребуют обычной версионированной миграции. Проверка «схема R2 → R3 на той же БД с сохранённым журналом» должна стать явным upgrade-gate, когда совместимость начнёт обещаться.
