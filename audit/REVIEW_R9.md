## R9-01 — P2 — повторный выбор проекта очищает состав, а возврат зависит от загрузки промежуточного проекта

**Где:** [useAddRehearsalForm.ts:227](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/src/features/calendar/hooks/useAddRehearsalForm.ts:227), безусловный сброс :230; [useParticipantSeed.ts:47](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/src/features/calendar/hooks/useParticipantSeed.ts:47), ранние выходы :50–51. Вызов для уже выбранного пункта доступен в [AddRehearsalScreen.ts:357](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/src/features/calendar/screens/AddRehearsalScreen.tsx:357).

**Клетка: просто × серьёзно. Покрытие правкой причины: неполное.** При редактировании уже существующей репетиции обычный повторный выбор её же проекта приводит к отправке пустого состава. Серверный контракт применяет этот список как удаление участников и их ответов. Это влияет на существующую репетицию и её участников, а не только на оформление формы.

`handleSelectProject` всегда делает `setSelectedMemberIds([])`, даже если id проекта не изменился. Новый хук начального состава хранит только последний успешно заполненный проект в `seededFor`; для прежнего id повторно ничего не делает. В edit mode он вовсе не участвует. Два механизма управления одним состоянием не согласованы.

**Воспроизведение на настоящем AddRehearsalScreen:**

1. В планировщике проекта A выбрать людей `3` и `7`, открыть создание. После загрузки форма правильно показывает `[3, 7]`.
2. Открыть выбор проекта и нажать уже отмеченный A. Фактический состав становится `[]`, хотя человек не менял ни проект, ни участников.
3. Для существующей репетиции A с сохранённым составом `[9]` выполнить то же и нажать «Обновить». В независимой пробе реальный `useAddRehearsalSubmit` вызвал `rehearsalsAPI.update` с `participant_ids: []` вместо `[9]`. На границе API стоит mock; последствие на сервере следует из `settleRoster`/`clearRoster`, которые удаляют строки при пустом списке.

Связанный сценарий показывает, почему одного условия для повторного нажатия недостаточно:

- A заполнен из планировщика → перейти в B → загрузка B завершилась ошибкой → вернуться в A → A успешно загружен, но выбор остаётся `[]`: `seededFor` всё ещё равен A.
- A → **успешно загруженный** B → A даёт правильный `[3, 7]`, потому что B успел изменить `seededFor`.

Исход возврата зависит от постороннего результата загрузки B. Фраза «один раз на проект» также не означает кэш посещённых проектов: код хранит только последний id и после успешного B заново применяет начальный состав A. Сам выбор такой политики возврата допустим; она должна работать одинаково при успехе и отказе загрузки B.

**Проверки:** `selecting the already current project preserves its participant choice`, `returning to the planner project after another project failed still starts with its people`, `editing and selecting the same project does not erase the saved roster on update` — все падают на сравнении ожидаемого состава с `[]`. Успешный A → B → A отдельно зелёный.

**Исправление причины:** один согласованный переход проекта должен управлять и сбросом выбора, и его инициализацией. Выбор того же проекта сохраняет текущий состав; настоящий переход не должен зависеть от того, успел ли промежуточный запрос завершиться. Сохранять различие между намеренно очищенным составом и составом, который ещё не инициализирован. Часть цепочки (`handleSelectProject`) существовала до этого коммита; замечание — о неполном исправлении поведения формы, а не о новом серверном регрессе.

## R9-02 — P2 — пока состав не готов или не загрузился, форма сохраняет репетицию без людей планировщика

**Где:** [AddRehearsalScreen.ts:264](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/src/features/calendar/screens/AddRehearsalScreen.tsx:264), кнопка не учитывает готовность участников; [useRehearsalMembers.ts:38](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/src/features/calendar/hooks/useRehearsalMembers.ts:38), отказ превращается в пустой список без отдельного статуса ошибки; [useParticipantSeed.ts:50](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/src/features/calendar/hooks/useParticipantSeed.ts:50), состав ждёт загрузки. В [useAddRehearsalSubmit.ts:73](/Users/vadimfertik/Desktop/reh_app-review/rehearsal-calendar-native/src/features/calendar/hooks/useAddRehearsalSubmit.ts:73) текущий выбор отправляется как полный список.

**Клетка: просто × мелко. Покрытие правкой причины: неполное.** Достаточно обычного медленного соединения либо ошибки загрузки. Созданную репетицию можно отредактировать, но перенос выбранных людей не выполняется и требуется повторная работа. Попадания в доли секунды не нужно: загрузку можно удерживать сколько угодно.

**Воспроизведение:** открыть форму из планировщика A с `prefilledMemberIds: ['3', '7']`, датой и временем. Пока `getMembers(A)` не ответил, нажать «Создать». Кнопка доступна; фактический запрос:

```js
rehearsalsAPI.create('A', {
  startsAt: '2026-11-10T10:00:00.000Z',
  endsAt: '2026-11-10T12:00:00.000Z',
  participant_ids: [],
  title: undefined,
  location: undefined,
});
```

Если запрос отклонён, показывается Alert, список пуст и загрузка закончена. После закрытия сообщения «Создать» точно так же отправляет `[]`. Это не явный выбор пользователем пустого состава: исходно он выбрал двух людей в планировщике. Сервер принимает пустой список по своему действующему контракту; блокировки отправки на этом уровне нет.

**Проверки:** `a pending membership load must not submit the planner rehearsal with an empty roster` и `a failed membership load must not submit the planner rehearsal with an empty roster` — оба падают: вместо отсутствия запроса получен один вызов `create` с `participant_ids: []`. Реальны экран, форма, загрузка, начальный выбор и submit; подменена граница API.

**Исправление причины:** у состава активного проекта должно быть явное состояние готовности/ошибки, которое использует отправка формы. При ошибке нужен определённый путь повтора либо выхода; пока начальный состав не определён, сохранение не выполняется. Намеренный пустой состав после успешной загрузки остаётся допустимым. Это продолжение механизма DP02 и может быть исправлено вместе с R9-01.
