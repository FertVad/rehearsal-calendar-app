# Production: состояние, ограничения и действия человека

Источник: сообщение Вадима от **18 сентября 2026**, основанное на независимых
измерениях. Агент эти production-проверки не повторял и секреты не читал.
Эта запись дополняет исторические отчёты R0/H01/A02, не меняя их evidence.

## Сообщённое состояние

- Прямой `SELECT 1` по боевому DATABASE_URL возвращает SQLSTATE **53000**, `Your account or project has exceeded the compute time quota`, примерно за 1,5 с. Сообщённая причина — исчерпание месячных 100 CU-часов бесплатного Neon.
- `/`, `/privacy`, `/support`, `/.well-known/apple-app-site-association`, `/admin/`, `/api/health` возвращают HTTP500 `FUNCTION_INVOCATION_FAILED`. Это измерения пользователя, не текущий run агента.
- Сообщённый вывод по коду и логам Vercel: весь сайт обслуживает одна функция; отказ PostgreSQL запускает SQLite fallback, SQLite не открывает файл в read-only окружении, необработанное исключение при startup не даёт загрузиться модулю. Поэтому недоступны и страницы/health, не нуждающиеся в БД. Цепочка startup отличается от исправленного A02 request middleware.
- Локальные исправления не деплоились. Успех Docker PostgreSQL и Jest fixtures не означает доступности production. Отказ квоты не считать новым дефектом кода или регрессом локальной ветки; повторную диагностику и обход не выполнять.
- `server/.env` содержит **боевую** строку подключения. Любой обычный локальный запуск entrypoint может подключиться к Neon и разбудить compute. Тестовый контекст обязан задаваться отдельно, без загрузки этого файла.

По сообщению Вадима два scheduler с интервалом 15 минут удерживали compute
активным значительную часть суток; Neon засыпает через 5 минут простоя.
Это причина запрета добавлять любой production polling по расписанию.
Вопрос оплаты/перехода на Neon Launch решает Вадим, когда production понадобится.

## Обязательная остановка перед доступом

Перед зависимым действием написать отдельной строкой:

> Нужен production: <конкретное действие>. Ожидаю решения Вадима.

До ответа действие не выполнять. Запрет распространяется на:

1. Любое обращение к `rehearsly.me`, включая read-only HEAD/GET/health/static.
2. Любое подключение к боевой БД, чтение фактической схемы, данных или migration ledger.
3. Deployment smoke и проверку production-переменных Vercel.
4. Push ветки и первый удалённый запуск `Application checks`, включая job `postgres-a02`. Сам этот job использует одноразовую БД, но отправка ветки и удалённый запуск всё равно требуют решения Вадима.

Известный отказ не лечить повторными запросами, fallback на другую удалённую БД
или новой схемой обхода. Оплата Neon не означает автоматического разрешения
на push, deploy, миграции или включение reminders: разрешённый scope подтверждается отдельно.

### Разрешение на отправку ветки и CI — 18 сентября 2026

После обсуждения локальной ветки Вадим разрешил отправить
`codex/systematic-repair` в GitHub и запустить первый `Application checks`.
Это разрешение не включает deployment, production smoke, доступ к Neon или
переменным Vercel. Ограничения на reminders сохраняются.

Read-only проверка метаданных GitHub показала предыдущие автоматические Preview
deployments. Поэтому перед push в `server/vercel.json` задано
`git.deploymentEnabled["codex/systematic-repair"] = false` — штатное
[отключение Git deployments для конкретной ветки](https://vercel.com/docs/project-configuration/git-configuration).
Изменение не отключает CI. Статическая проверка `Application checks` подтвердила
использование fixtures/одноразового PostgreSQL и отсутствие production secrets
или запуска `server.js`. Результат удалённого запуска следует смотреть в GitHub
Actions по конкретному commit; историческое NOT_RUN в локальных отчётах не
переписывается задним числом.

## OPS-IA01 — проверка APPLE_CLIENT_ID человеком

**Статус:** NOT_RUN. **Finding:** IA01 — [READY_FOR_CHECK](REMEDIATION_IA01.md):
локальный guard и проверки завершены на `0dc7666`, deployment condition ещё не подтверждён.
**Исполнитель:** Вадим или уполномоченный им человек с доступом к Vercel.
**Когда:** перед закрытием deployment-части IA01, после отдельного решения Вадима.
Карточка готова к ручной проверке после решения Вадима. Менять переменные,
запускать приложение или redeploy без отдельного решения не требуется.
Просмотр одной настройки не расходует дополнительный Neon compute;
[оценка будущей DB-проверки](NEON_COST_ESTIMATE_2026-09-18.md) приведена отдельно.

1. Выбрать нужный Vercel project и среду **Production**; зафиксировать безопасный идентификатор проекта и проверяемого deployment, без секретов.
2. Проверить, что `APPLE_CLIENT_ID` задан именно для этой среды, не пуст и не состоит из пробелов. Человек сверяет его с ожидаемым Apple audience приложения/способа входа.
3. Установить, что проверенное значение относится к активному deployment: наличие новой переменной в настройках само по себе не доказывает, что уже работающий deployment её получил. Redeploy без отдельного решения не выполнять.
4. Передать результат: дата/UTC, project/environment/deployment, `present: yes/no`, `nonempty: yes/no`, `expected audience matches: yes/no/unknown`, `active deployment binding: confirmed/unknown`. Значения секретов, JWT и весь экспорт environment не присылать.
5. При отсутствии/пустом/неподтверждённом значении deployment-проверку не считать PASS. Решение о настройке и выпуске принимает Вадим.

Исходная стартовая проверка `server.js` требовала JWT_SECRET и CRON_SECRET,
но не APPLE_CLIENT_ID. В исправленной ветке pure helper диагностирует Apple
configuration и выключает только Apple login при неверном audience. Факт
успешного старта всего сервера по-прежнему не подтверждает deployment condition IA01.
Локальные тесты исправления отдельно подтвердили отказ Apple login
при отсутствии/пустом audience и отклонение токена чужого приложения.
Одно наличие переменной в Vercel не заменяет исправление и проверку guard.
