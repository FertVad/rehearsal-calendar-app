## Причина и исправленный контракт

Один смешанный `invites.js` был смонтирован под `/api/native/invite` и
`/api/native/projects`, а middleware лимита находился только на первом префиксе
в `app.js`. После 20 обращений к каноническому URL можно было продолжать проверку
кодов через `POST /api/native/projects/:code/join`. Дополнительно MemoryStore
считал запросы отдельно в каждом экземпляре приложения.

Управление приглашением отделено от preview/join. IP middleware установлен
непосредственно в цепочках операций, а оба join URL используют один массив
handlers. Счётчики сохраняются в общей БД, поэтому смена кода, alias или
экземпляра приложения не открывает новый бюджет. Успешные ответы и действия
управления приглашениями сохраняют прежний контракт.

| URL / метод | Поведение после изменения |
|---|---|
| `GET` / `HEAD /api/native/invite/:code` | Публичный preview, общий IP бюджет |
| `POST /api/native/invite/:code/join` | IP бюджет → authentication → account бюджет → проверка кода → join |
| `POST /api/native/projects/:code/join` | Сохранённый legacy alias, та же цепочка join |
| `GET` / `POST` / `DELETE /api/native/projects/:projectId/invite` | Управление приглашением, прежняя проверка активного owner/admin |
| `GET` / `POST` / `DELETE /api/native/invite/:projectId/invite` | Явно сохранённые management aliases, та же admin policy |
| `GET /api/native/projects/:code` | Прежний маршрут project detail: authentication и membership; публичным preview не становится |
| `GET /invite/:code` | HTML открытия приложения, без поиска приглашения и запросов к БД |

`projectInvites.js` содержит управление, `inviteRedemption.js` — preview/join;
старый смешанный router удалён. HEAD наследует GET-цепочку Express и также тратит
IP бюджет. Произвольные методы и неполные URL не получают отдельного пути
к поиску кода или записи членства.

## Бюджеты и хранение

| Ограничение | Значение / поведение |
|---|---|
| IP | 20 попыток за календарную минуту часов БД, суммарно для preview и обоих join URL |
| Account | Дополнительно 20 попыток join за минуту для прошедшего authentication пользователя, независимо от IP и alias |
| Счётчик | Первые 20 допущены, 21-я и следующие отклоняются; значение насыщается на 21 |
| Account cardinality | Одна строка на `native_users.id`, FK с `ON DELETE CASCADE` |
| IP cardinality | Не более 10 000 строк; заполненное хранилище отклоняет новый ключ с 503, активные ключи не вытесняются |
| Очистка IP | При выделении нового ключа удаляется максимум 64 истёкших строки; scheduler, таймер и polling отсутствуют |
| Отказ бюджета | 429 и `Retry-After` от 1 до 60 секунд, без поиска кода и операций членства/уведомлений |
| Отказ хранилища | 503 с общим сообщением, без SQL, адресов и внутренних имён таблиц в ответе |

`008-invite-rate-limits.sql` добавляет account/IP таблицы и singleton gate.
Та же добавка внесена в baseline SQL. CHECK constraints ограничивают окно,
счётчик, формат digest и значение gate. Повторное применение не сбрасывает
существующие счётчики. Миграция не читает и не меняет бизнес-данные.

IP принимается из `req.ip` по существующей политике `trust proxy = 1`.
Некорректный адрес не превращается в произвольный ключ. IPv4 и его IPv4-mapped
IPv6 записи, включая hexadecimal spelling, нормализуются в один адрес;
обычные IPv6 адреса группируются по /56. В SQL передаётся только HMAC-SHA256
от нормализованного ключа с `JWT_SECRET`, сырой IP этим сервисом не сохраняется
и не логируется. В production пустой secret даёт отказ. Одинаковый стабильный
secret у всех экземпляров — необходимое условие общей IP идентичности.

Атомарные account UPSERT и IP UPDATE используют часы БД; запоздавший statement
не возвращает окно назад. PostgreSQL выделяет новые IP ключи и удаляет истёкшие
под блокировкой gate в одной транзакции. Уже существующие ключи обновляются
без этой общей блокировки. Повторная проверка после ожидания gate исключает
двойное выделение; изменение gate согласовано с фактическим числом удалений.
Внешний expiry predicate у DELETE защищает строку, которую параллельный запрос
уже обновил до текущего окна. Детерминированная PG проверка подтверждает реальное
ожидание DELETE через `pg_blocking_pids`, затем сохранность строки и её бюджета.
Контрольная временная копия без внешнего predicate теряет строку и падает именно
на этом assertion: [отрицательная проверка](evidence/B04/postgres-prune-negative-control.txt).

## Порядок отказов и совместимость

Неавторизованный или отклонённый authentication запрос join расходует IP бюджет,
но не создаёт account строку и не читает приглашение. Account identity берётся
только из `req.userId` после `requireAuth`, а не из body, query или параметра URL.
Отклонённый бюджет останавливает выполнение до invite lookup, membership read/write
и уведомлений. Отказ account хранилища также не пропускает join.

Допускаются прежние восьмизначные коды из `23456789ABCDEFGHJKMNPQRSTVWXYZ`
и legacy коды из 32 hexadecimal символов. Поиск остаётся точным: регистр
не исправляется автоматически. Неверный формат даёт 404 после бюджетов, но до
invite SQL; отсутствующий код — 404, истёкший — 410, действующее членство — 400.
Обычный join и повторная активация членства сохраняются вместе с уведомлением
руководителей проекта. Сами эти бизнес-операции не перепроектировались в B04.

Middleware выставляет `Cache-Control: no-store`, включая отказ хранилища.
После получения бюджета сохраняются `RateLimit-Policy: 20;w=60`,
`RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`; для join remaining
учитывает минимум уже израсходованных IP/account allowances. При 429 добавляется
`Retry-After`, тело сохраняет прежнее сообщение о превышении частоты.

## Перед выпуском: карточка человека B04-RELEASE

**Статус: NOT_RUN.** Production schema/ledger, migration, deployment smoke,
ingress и мобильный сценарий на стенде не проверялись. Физическое устройство
не требуется для доказательства серверного HTTP bypass и общей цепочки aliases;
мобильная проверка ниже относится к совместимости будущего выпуска.

1. Соблюсти [границу production](PRODUCTION_ACCESS.md): до обращения отдельно сообщить «Нужен production: проверить фактическую схему и migration ledger для migration008. Ожидаю решения Вадима». Продолжать только после решения. Из локальной fixture не выводить наличие таблиц в production.
2. На изолированной копии/стенде применить именно additive migration008 и проверить PK/FK/CHECK, gate и повторное применение. Не запускать вслепую `--baseline`, старый полный migration runner или `server/.env`: R2 ещё открыт. Затем отдельно согласовать применение migration008 к production **до серверного deployment**, иначе preview/join закономерно вернут 503.
3. На согласованном ingress проверить, что доверенный proxy правильно формирует адрес клиента и не позволяет подменять его произвольным `X-Forwarded-For`. Проверить общий бюджет разных экземпляров и одинаковый JWT secret. Локальная подстановка XFF в тестах не доказывает свойства Vercel ingress.
4. На мобильной тестовой сборке с синтетическим backend проверить открытие short/legacy ссылки, preview, обычный join, истёкший код, уже активное членство, понятность 429/503 и повтор после восстановления. Убедиться, что смена URL не обходит бюджет. Production credentials и нагрузка на боевую БД для этого не нужны.
5. После отдельного решения о серверном выпуске выполнить только согласованный deployment smoke и записать фактические результаты. Публикация мобильной сборки — отдельное действие. Напоминания остаются выключенными; новые расписания не создаются.

Откат: additive таблицы можно оставить при возврате приложения к предыдущей
версии, но сам возврат восстановит обход B04. Это решение оператора, а не
безопасный автоматический recovery. Не удалять rate-таблицы при работающем новом
коде и не очищать IP таблицу отдельно от gate. Плановое обслуживание и ротация
secret должны учитывать сброс IP идентичности и текущих бюджетов.

## Границы результата

Минуты фиксированные: на границе допустим всплеск; это не rolling window,
общий предел параллельных запросов или защита от распределённого перебора со
множеством аккаунтов/IP. Gate предполагает отсутствие посторонних изменений
IP таблицы; обслуживание должно сохранять согласованность строк и `key_count`.
Ёмкость и 64 удаления ограничивают хранение/очистку, но не доказывают latency
на production объёмах и не заменяют PostgreSQL statement timeout.

Auth/admin лимиты по-прежнему используют process-local MemoryStore: IS02
не объявляется полностью исправленным. B03 не менялся. Общий startup/fallback,
bootstrap SQL и migration ledger относятся к R2 и остаются открытыми.
При настроенном, но недоступном PostgreSQL именно invite budgets отказывают,
не переходя на локальный SQLite. SQLite fixtures доказывают portable SQL;
существующий async adapter не гарантирует очередь конкурентных транзакций,
поэтому полноценная SQLite runtime/concurrency поддержка здесь не заявляется.
Известный отказ Neon не перепроверялся; production smoke остаётся NOT_RUN.
