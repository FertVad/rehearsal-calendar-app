## Причина и контракт

Маршрут `GET /api/native/projects/:projectId/members/availability` сначала
разворачивал произвольный диапазон в массив строк и только потом проверял
членство. Даже посторонний зарегистрированный пользователь мог занять event loop
генерацией миллионов дат. После проверки прав объём также рос без верхней
границы по участникам, записям и разрезанию длинных событий на дни.

Теперь вход проверяется за ограниченное число операций; членство и бюджеты
проверяются до разворачивания дат и чтения занятости. Ответ либо полный в рамках
запроса, либо явная ошибка. Усечение данных с успешным ответом недопустимо:
планировщик трактует пропущенные busy-записи как свободное время.

| Ограничение | Значение / поведение |
|---|---|
| Даты | Реальные `YYYY-MM-DD`, годы 0001–9999, начало не позже конца |
| Режим запроса | Только `date` либо пара `startDate`/`endDate`; массивы, объекты и смешанный режим → 400 |
| Диапазон | 1–90 дней включительно; 91-й день → 400 до цикла |
| Участники | До 100 выбранных активных участников проекта; IDs дедуплицируются и пересекаются с членством |
| Совместный объём | До 3100 пар «участник × день» |
| Записи из БД | До 5000; SQL читает максимум 5001 строку для обнаружения превышения |
| Сегменты времени | До 20000 суммарно после разрезания событий на дни |
| Ответ | До 1 MiB фактического JSON в UTF-8, с консервативным учётом при построении |
| Частота | 60 запросов за календарную минуту часов БД на account, общие для всех проектов/экземпляров; далее 429 + Retry-After |
| Превышение объёма | 422, `AVAILABILITY_BUDGET_EXCEEDED`, без частичного `availability` |
| Хранилище счётчиков недоступно | 503 до чтения занятости; восстановление без перезапуска |

Даты, IDs и размеры проверяются до SQL бизнес-выборок. ID соответствует
PostgreSQL INTEGER, поэтому `2147483648`, `2x`, пустые значения и неоднозначные
query-параметры не превращаются в SQL500. Неверная/отозванная сессия получает 401,
неактивное или отсутствующее членство — 403. Ограничения находятся в операции,
поэтому HEAD и новые mounts того же router используют тот же бюджет.

## Реализация

- Числа собраны в `shared/contracts/memberAvailabilityLimits.json`, который читают сервер и клиент. Расширение дат отделено от строгого разбора; оно вызывается только после membership и проверки числа участников.
- Рoster фильтруется в SQL, ограничивается 101 строкой для обнаружения превышения. Явный небольшой `userIds` позволяет читать подмножество большого проекта. `hasData` сохраняет прежнюю семантику через `EXISTS` для каждого ограниченного набора пользователей, без выгрузки всей истории.
- Строковые поля из БД также имеют ограниченные SQL-проекции: имя/фамилия до 4097 символов с отказом сверх 4096 UTF-16 единиц, type до 33 с отказом сверх 32, timezone до 129 с отказом сверх 128. Ответ не содержит молча обрезанных значений.
- Каждый record проходит только по запрошенным, уже ограниченным датам. Сравнения дней числовые: переход локального времени или all-day интервала в год 10000 не теряет занятость на 9999-12-31. Один Intl formatter используется в пределах запроса; глобальный растущий cache не создаётся.
- `007-member-availability-rate-limit.sql` добавляет одну строку счётчика на реального пользователя с FK CASCADE. Атомарный UPSERT использует время БД и общий row lock, счётчик ограничен значением отказа 61. Старые окна переиспользуются; отдельного cleanup, polling или scheduler нет. Запоздавший запрос не сбрасывает более новое окно.
- При настроенном PostgreSQL локальный SQLite fallback для этого бюджета запрещён. Общая старая логика startup/fallback в `database/db.js` относится к R2 и не объявляется исправленной.
- Новая таблица включена также в существующий baseline SQL. Это не исправляет смешанный SQL-диалект старого bootstrap и недостатки migration runner: F01/F02/FT01/FT02 остаются открытыми.

## Клиент и совместимость

Пресеты 7/30 дней и формат успешного API-ответа сохранены. Custom picker
запрещает период длиннее 90 дней до построения календарных отметок и показывает
объяснение на RU/EN/ES/DE. Hook повторно проверяет диапазон до сетевых запросов
и генерации рекомендаций. Для нового, ожидающего или отклонённого диапазона
старые рекомендации скрываются: ошибка 400/422/429/503 не означает «все свободны».

**Граница поддержки:** текущий Smart Planner запрашивает всех участников проекта;
его фильтр участников работает после загрузки и не сокращает API-запрос.
Поэтому для 100 участников доступны до 31 дня, для 90 дней — до 34 участников,
а проект с более чем 100 активными участниками этим экраном пока не планируется.
Сервер возвращает явную ошибку. Автоматическое разбиение на неограниченное число
запросов не добавлено: оно вернуло бы неограниченную нагрузку и потребовало бы
нового согласованного snapshot/pagination-контракта. Single-date API с явным
`userIds` поддерживает ограниченное подмножество большого проекта.

Серверная защита действует и для старой мобильной сборки. Клиентские guards и
поведение picker появятся после отдельной сборки/выпуска приложения.

Истечение окна проверяется изменением только fixture, без ожиданий и расписания.

200. Контейнер удаляется с проверкой ownership, внешние соединения запрещены.

Пока R2 не закрыт, штатный migration runner нельзя считать проверенным безопасным путём.
2. На изолированной копии/стенде применить именно additive migration007, проверить PK, FK CASCADE и CHECK constraints; повторное применение не меняет строки. Проверить valid request200, общий 429 двух экземпляров и recovery. Затем отдельно согласовать application migration007 на production **до серверного релиза**. Без неё availability будет возвращать503 по правилу fail closed.
3. На тестовой сборке телефона, направленной в согласованный тестовый backend с синтетическими данными, проверить пресеты7/30, custom90 и попытку91 дней, понятность сообщения и возврат к допустимому периоду. 5. Перед серверным выпуском оператор подтверждает новую таблицу и разрешённый deployment; после выпуска smoke выполняется только в согласованном объёме. Новая мобильная сборка и её распространение — отдельные действия. Reminders остаются выключенными.

предел одновременно выполняемых запросов. Масштаб/планы DB-запросов на реальных
объёмах, общие auth/IP лимиты и остальные операции проверяются отдельно.
