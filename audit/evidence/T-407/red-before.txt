What failed (supervisor's checks of T-406, c8b1b5c, 25.11.2026 03:25, and again at ~04:00)
-------------------------------------------------------------------------------------------
All 11 flows of the set failed with maestro.DeviceUnreachableException. Only the
first, 09-invite-during-onboarding, ever ran: the driver died in it and every
flow after it found no driver. Four of the five T-406 runs died at this spot.

Cause, from the logs (lines copied below; the folders are pruned after 3 days)
-------------------------------------------------------------------------------
1. The tap on "Sign In" (sign-in-submit.yaml -> tap-and-see.yaml) is taken: the
   keyboard goes away and the app goes on. Not a lost tap: no backboardd, the
   tap's own subflow saw the button go.
2. Right after it the app's keyboard (UIKit, in the app's process) asks for the
   "Save Password?" sheet: signalAutofillUIBringup, then
   SFPasswordSavingRemoteViewController "Requesting remote view controller ...
   from service com.apple.SafariViewService", and SpringBoard launches
   SafariViewService to host it.
3. com.apple.WebUI AutoFillPasswords = false (noPasswordOffer, T-246) does not
   stop that. The setting is read by SafariViewService itself once it is up; it
   then takes the sheet down unseen 1-2 s later. So the sheet was asked for at
   EVERY sign-in of every run, green ones too (table below) - flow 01's
   assertNotVisible "Not Now" cannot see that, because the sheet is never drawn.
4. Maestro's driver (2.11.0), reading the screen, runs "Fetch Safari WebView
   hierarchy": while SafariViewService runs it queries it for WebViews. Asked
   while the service was still starting (its XCTest bootstrap "Got availability
   notification from test daemon" at the same millisecond), XCTest answered
   kAXErrorAPIDisabled three times (8.5 s) and failed the driver's one test,
   testHttpServer. That is the end of the driver.
5. On a freshly booted simulator (every supervisor run boots it anew) the
   service's first start is slow; the first sign-in of the run meets it.
   09-invite is the first flow of the set.

Not T-246's race (kAXErrorInvalidUIElement in the status-bar query of an InputUI
scene): here kAXErrorAPIDisabled in the WebView query of SafariViewService.

What makes the keyboard ask: ManagedConfiguration's allowPasswordAutoFill
--------------------------------------------------------------------------
In the iOS 26.5 runtime, UIKitCore's -[UIKeyboardImpl handleAutofillCredentialSaveIfNeeded:]
sits next to -[UIKeyboardPreferencesController isPasswordAutoFillAllowed];
ManagedConfiguration has isPasswordAutoFillAllowed / MCFeaturePasswordAutoFillAllowed
(the "allowPasswordAutoFill" restriction). On the e2e simulator, as the base left it:

  data/Library/Preferences/com.apple.WebUI.plist:  "AutoFillPasswords" => false
  data/Library/UserConfigurationProfiles/UserSettings.plist: {}
  data/Library/UserConfigurationProfiles/EffectiveUserSettings.plist:
      restrictedBool.allowPasswordAutoFill.value = true

The experiment: flow 01 (one sign-in), the same app and runner, only the user setting differs.

  UserSettings.plist = { restrictedBool = { allowPasswordAutoFill = { value = false } } }, written with the device shut down
  $ npm run e2e -- e2e/flows/01-login.yaml
  [Passed] Sign in (1m 24s)
  effective allowPasswordAutoFill: false        (iOS worked it out at boot)
  e2e/out/artifacts/2026-11-25_045644: Sign in | sheet at - | signalAutofillUIBringup 0 | APIDisabled 0

  UserSettings.plist = {} again (as the base leaves it)
  $ npm run e2e -- e2e/flows/01-login.yaml
  [Passed] Sign in (1m 52s)
  effective allowPasswordAutoFill: true
  e2e/out/artifacts/2026-11-25_050237: Sign in | sheet at 17:06:12.986 | signalAutofillUIBringup 3 | APIDisabled 0

With allowPasswordAutoFill off nothing asks for the sheet and SafariViewService
is not started; with it on (the base) it is, at every sign-in. The red run above
was taken after the second experiment, on the base's state.
